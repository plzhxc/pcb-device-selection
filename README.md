# 器件选型阶段（device_selection）

把已确认的需求条目转换成**有证据、可讨论、可确认**的候选器件清单，并把用户最终
选定的器件交给下游的网表生成流程。

本目录是郑智齐负责的器件选型阶段的独立工作区。阶段设计见
[docs/器件选型阶段设计.md](docs/器件选型阶段设计.md)。

---

## 1. 这个工具做什么

| 步骤 | 做什么 | 不会做什么 |
| --- | --- | --- |
| 生成选型条件 | 把需求条目变成类别、数量、硬性条件、偏好条件 | 不修改需求，不改写上游结论 |
| 候选召回 | 按型号精确查，或按器件类别从真实目录里找同类器件 | 不用模型记忆补造型号 |
| 参数核对 | 逐条比对电压、电流、频率、封装、温度等，判成满足/不满足/未知 | 不把「查不到」当成「满足」 |
| 展示与讨论 | 网页端列表加对话，支持保留/排除/待讨论/确认 | 不替用户拍板 |
| 交接下游 | 只导出用户选定的器件，转成 `pcbagent.netlist_input.v1` | 不导出待讨论或已淘汰的候选 |

三条不可让步的红线：**候选只能来自真实检索**、**未知不算满足**、**价格缺失按待确认（不按 0 元算）**。

---

## 2. 输入是什么

一份 JSON，schema 为 `pcbagent.requirement_spec.v1`，放在 `specs/` 或 `cases/` 下。

```jsonc
{
  "schema": "pcbagent.requirement_spec.v1",
  "requirement_version": "req-demo-0001",       // 需求版本，会原样带进输出
  "project": { "name": "…", "summary": "…" },
  "global_constraints": { "budget_total_cny": 120, "currency": "CNY" },
  "selection_items": [                          // 一个选型项 = 一类要选的器件
    {
      "id": "SEL-001",                          // 唯一编号，会作为下游 module.id
      "module_name": "24V 转 5V 降压电源",       // 可选，下游 module.name
      "module_type": "power",                   // 可选，下游 module.type
      "category": "dc_dc_power_converter_chip",
      "leaf_code": "l_step_down_dc_dc_converter", // 器件类别，决定按什么召回
      "quantity": 2,
      "related_requirements": ["F01"],          // 关联的需求编号，用于追溯

      "hard_conditions": [                      // 违反即淘汰
        { "field": "topology", "op": "contains", "value": "Buck",
          "reason": "必须是降压拓扑", "related_requirement": "F01" }
      ],
      "preferred_conditions": [                 // 只影响提示与排序
        { "field": "output_current", "op": ">=", "value": 5, "unit": "A" }
      ],

      "specified_device": { "model": "TPS5450DDAR", "intent": "reference" }
    }
  ]
}
```

**条件比较符**：`>=` `<=` `>` `<` `==` `!=`（数值）、`cover`（器件能力区间要覆盖需求区间）、
`is` `is_not` `in` `not_in` `contains` `not_contains`（文本）。

**`specified_device.intent`**：`must` / `preferred` / `reference`，对应需求侧的
「必须使用 / 优先考虑 / 仅作参考」。用户提到某个型号不等于必须选它。

## 3. 输出是什么

一次选型产出三样东西，对应三种不同状态：

| 文件 | 内容 | 谁用 |
| --- | --- | --- |
| `output/<名称>.json` | **候选清单**（`pcbagent.candidate_set.v1`）：候选、逐条判定、证据、成本状态 | 人看，网页展示 |
| `output/decisions.json` | **用户决定**（`pcbagent.device_decisions.v1`）：保留/排除/待讨论/已确认及理由 | 人看，可追溯 |
| `output/netlist_input.json` | **下游交接**（`pcbagent.netlist_input.v1`）：只含用户选定的器件 | 网表生成流程 |

三者刻意分开：**资料核验状态**和**用户选择状态**是两个独立状态，证据不会因为
用户点了按钮就被改写。

候选清单里每个候选项含有 `model`、`supplier_part`（立创 C 编号）、
`unit_price_cny` 与 `price_status`、`evaluation`（`fit` / `confidence` /
`satisfied` / `violated` / `unknown` / `missing_evidence`）、`key_attributes`、
`missing_fields`。

`fit` 的判定口径：硬性条件违反 → `excluded`（淘汰，不进推荐）；硬性条件有未知 →
`conditional`（证据待补，不能算满足）；全部满足 → `recommended`；**一条条件都没有
→ `unjudged`（未核对，不算推荐）**。完整规则见下一节。

**下游交接文件已通过下游官方校验器**
（`netlist_end_to_end.generation_input.validate_generation_input`）。导出只带用户
「已确认」的器件；待讨论和排除的一律不导出；没有选定器件的选型项记进
`diagnostics.skipped` 说明原因，不用占位件凑数。

## 4. 判定器件选型条件的规则

这一节说明「满足 / 不满足 / 未知」这三个结论到底是怎么算出来的。**全部由代码算，
不由大模型判断。** 实现见 [src/evaluate.py](src/evaluate.py) 与 [src/units.py](src/units.py)。

### 4.1 一条条件长什么样

```json
{
  "field": "output_current",
  "op": ">=",
  "value": 5,
  "unit": "A",
  "hard": true,
  "reason": "下游峰值电流 4A，留余量",
  "related_requirement": "F02"
}
```

| 字段 | 含义 |
| --- | --- |
| `field` | 数据库里的字段名，必须落在允许改写的白名单里 |
| `op` | 比较符，见 4.2 |
| `value` / `unit` | 取值与单位；`unit` 会换算到基准单位后再比 |
| `hard` | `true` 是硬性条件（违反即淘汰），`false` 只作偏好与提示 |
| `reason` / `related_requirement` | 记录这条要求从哪来，供追溯 |

### 4.2 比较符的语义

| 比较符 | 含义 | 典型用途 |
| --- | --- | --- |
| `>=` `<=` `>` `<` | 数值比较，**方向是「器件能力是否够」** | 输出电流 ≥ 5A、压差 ≤ 0.5V |
| `==` | 取值落在要求点上 | 固定输出 3.3V |
| `!=` | 不等于该值 | 排除某个档位 |
| `cover` | **器件的能力区间要覆盖需求区间** | 输入电压范围、工作温度范围 |
| `is` / `is_not` | 文本相等 | 封装、拓扑 |
| `in` / `not_in` | 属于某个集合 | 允许多种封装 |
| `contains` / `not_contains` | 文本包含 | 接口、功能描述 |

**方向这一点最容易搞错。** 条件是「器件能不能满足需求」，不是「数值是否相等」：

- 需求「输入 24V」，器件写 `5.5V~36V` → 用 `cover`，判**满足**（器件能吃下 24V）
- 需求「输出电流至少 5A」，器件是 `5A` → 用 `>=`，判**满足**
- 需求「输出电压 3.3V」，器件是 `3.3V` → 用 `==`，判**满足**；器件是 `5V` → **不满足**

### 4.3 三态判定：满足 / 不满足 / 未知

每个条件一定落到这三态之一。判成**未知**的情形包括：

- 器件记录里**没有这个字段**；
- 字段存在但被标为缺失（`is_missing`）或「应该采到却没采到」（`EXPECTED_BUT_MISSING`）；
- 两边**单位对不上**或单位无法识别；
- 该字段是纯文本，而条件要求数值比较。

> **红线：未知绝不当满足。** 缺数据不能显示成通过，这是整个阶段最不能让步的一条。

### 4.4 单位归一化：四道闸门

手册和参数表里的数字写法很乱，直接比较会出错。取值依次过四道闸：

1. **文本优先** —— 能解析出带单位的文本就用文本，只有在文本解析不了时才退回数值列。
   （起因：TPS5450 的开关频率文本是 `500kHz`，数值列却是 `500` 配 `Hz`，直接比差 1000 倍。）
2. **换算到基准单位** —— 支持 SI 前缀，统一到 V / A / Hz / F / H / Ω / W / °C / s。
   条件写的 `kHz`、`mA` 也走同一套换算，两边单位一致后才比。
3. **严格解析** —— 整段文本要么就是一个量（`5A`、`5.5V~36V`），要么不算数值。
   否则 `SOP-8-EP-150mil` 会被解析出 `-8` 当成数值参与比较。
4. **单位族校验** —— 每个字段只接受自己那一族的单位：电压字段只收 V，电流只收 A，
   频率只收 Hz……否则 AMS1117 那句「输出电压……通过一个 22µF 的电容」会把 22µF 当成输出电压。

范围写法支持 `~`、`～`、`—`、`–`、`...`、`to`、**以及中文的「到 / 至」**
（`4.5V 到 5.5V`、`7 V 至 44 V`）。

### 4.5 证据来源分三级

| 来源 | 标记 | 怎么用 |
| --- | --- | --- |
| 结构化参数表 | `PROVEN` | 直接采信，注明 `device_id` 与来源表 |
| 结构化表里缺，但被标为应有 | `EXPECTED_BUT_MISSING` | 先判**未知**，再去数据手册找 |
| 数据手册片段 | `DATASHEET` | 补上取值并**带原文引用与页出处**，标 `needs_review` |

手册取到的值参与判定时，结论里会写明来自哪一页，例如
`器件 1.2V <= 条件 1.5V｜来源：数据手册「1. Description」`。

### 4.6 结论（`fit`）怎么算

| 结论 | 触发条件 | 界面显示 |
| --- | --- | --- |
| `recommended` | 无淘汰、无未知 | 绿色「推荐」 |
| `acceptable` | 无淘汰，只有偏好类未知 | 绿色「可接受」 |
| `conditional` | 有**硬性**条件处于未知 | 黄色「有条件」 |
| `unjudged` | **一条条件都没有** | 灰色「未核对」 |
| `excluded` | 任一硬性条件明确违反 | 红色「已淘汰」 |

`confidence` = 满足条数 ÷ 已判定条数，**只反映证据完整度，不是主观打分**。

> `unjudged` 是后加的：早期只要召回到候选就标「推荐」，等于把"从未核对"显示成绿色，
> 现在这种情况一律标「未核对」，并且不计入「有推荐」。

### 4.7 淘汰、阻塞与排序

- **淘汰**：任一硬性条件明确违反即淘汰，不进推荐列表。淘汰的候选仍会展示（默认折叠），
  并说明违反了哪条、器件值是多少，便于人工复核。
- **阻塞**：没召回到任何候选，或全部候选都被淘汰时，输出阻塞原因（例如
  「XL4016E1 违反 output_current（器件 12A）」），而不是硬凑一个答案。
- **未核对**：选型项没有任何可判定的条件时，明确标灰并提示
  「候选只来自类别召回，未做参数核对」，不算阻塞也不算是推荐。
- **排序**：按「是否推荐 → 证据完整度 → `device_id`」排。偏好条件目前**还没进入排序**，
  这是已知缺口（见第 10 节）。

### 4.8 价格规则

器件库没有价格字段。从预设元件库取到参考价就标注来源，取不到就显示
「单价待确认 · 数量 N · 未计入合计」——**不按 0 元计算**。

### 4.9 红线汇总

1. 候选只能来自真实检索，不用模型记忆补造型号；
2. 未知参数不能当作满足条件的证据；
3. 价格缺失标「待确认」，不按 0 元计算；
4. 本阶段不改写已确认需求；
5. 资料核验状态与用户选择状态分开记录；
6. 没有合适候选时输出阻塞条件，不硬凑答案；
7. 一条条件都没判过的候选，不许显示成「推荐」。

## 8. 网页端

界面是三栏：**左栏项目列表**（对接需求分析工作台的全部项目）→ **中栏对话** →
**右栏选型清单**。点左栏项目只「载入交接件」，真正执行选型要按上方运行条的
「开始选型」按钮——避免切换项目时反复触发、把对话区刷乱。详见第 15 节。

清单部分是一张表：

| 列 | 内容 |
| --- | --- |
| 器件型号 | 型号与厂商 |
| 关键参数 | 该类别优先级最高的几个参数原文 |
| 优势 | 满足的条件 |
| 劣势与风险 | 不满足的条件、待补证据、成本待确认 |
| 成本 | 单价 × 数量；查不到显示「待确认」 |
| 结论 | 推荐 / 可接受 / 有条件 / 已淘汰，附证据完整度 |
| 你的决定 | 保留（进短名单）/ 排除 / 待讨论 / 已确认（最终选定，点了就落盘） |

四个状态的含义与去向完全不同，**只有「已确认」会导出给下游**：

| 状态 | 含义 | 是否导出 |
| --- | --- | --- |
| 已确认 | 最终选定，可以进入网表生成 | ✅ |
| 保留 | 进候选短名单继续比较，还没拍板 | ❌ |
| 待讨论 | 有未知项或风险，等信息补齐 | ❌ |
| 排除 | 不再考虑 | ❌ |

每行可展开看逐条判定的依据。顶部「交付与交接」区有两个按钮：**查看最终候选清单**
（按选型项汇总状态、选定器件、成本与候选数量）和**导出下游交接文件**（显示是否通过
下游校验、带了哪些模块、哪些选型项没导出及原因）。两个面板都是**再点一次同一个
按钮即收起**；交接面板底部可以展开原始 JSON。

成本列的写法：单价已知时显示「¥单价 × 数量 = 小计」；器件库里没有价格证据时显示
「单价待确认 · 数量 N · 未计入合计」——那个 N 是选型项的数量，不是价格。

### 8.1 两个快捷操作

**一键确认推荐。** 运行条上会出现「一键确认推荐 (N)」，N 是**可以放心确认**的项数。
点一下就把这些项的首选标成「已确认」，不用逐个点。它的边界很明确：

| 结论 | 是否会被一键确认 |
| --- | --- |
| `recommended` / `acceptable` | ✅ 会 |
| `conditional`（硬性条件未知） | ❌ 跳过 |
| `unjudged`（没有可判定条件） | ❌ 跳过 |
| 已淘汰 / 没有候选 | ❌ 跳过 |
| 已经确认过的 | ❌ 跳过（不重复计数） |

跳过的项会在对话里逐条说明原因。**不核对的东西不会被一键确认**——否则等于把"未核对"
批量写进下游。确认后随时可以单行改成「保留」或「排除」。

**点型号看手册参数。** 清单里的器件型号是**可点击的**，点一下在附近弹出一个小窗，
显示：身份信息（型号、厂商、类别、立创编号、device_id）、关键参数、可展开的其余参数、
证据状态分布、以及最多 3 段数据手册原文（带页码与库名）。
点窗口外面或按 `Esc` 关闭，点另一个型号会直接切换。

### 对话现在能做什么

对话**以规则为主**：按固定顺序匹配句式，命中后执行一个真实动作
（查库 / 改条件 / 重算 / 记录决定），而不是生成一段话。规则接不住的句子才会交给
大模型做**意图翻译**（可选，见第 13 节），它给不出合规结果就退回总结。

| 你说 | 它的动作 |
| --- | --- |
| `为什么推荐 TPS5450DDAR` | 从真实属性表逐条列出满足/不满足/未知与出处 |
| `查一下 LM358` | 走目录精确查询，返回类别、厂商、核心等级、C 编号 |
| `把 SEL-002 的输出电流改成 800mA` | 改条件并真实重算 |
| `预算改成 100` | 改全局预算并重算 |
| `保留 X` / `排除 X` / `确认 X` | 记录用户决定并落盘 |
| `总结一下当前清单` | 汇总主推与阻塞 |

支持的字段词只有六个：输入电压范围、输出电压、输出电流、开关频率、工作温度、封装。
**超出这个范围的句子会退化成「总结清单」**，不会硬猜。接大模型时应只替换
「把人的说法翻译成条件」这一步，检索和判定仍然留在代码里。

## 11. 与需求分析工作台的接口

上游是 chenxin 的 `requirements_studio`（需求分析工作台），契约是
`pcbagent.requirement-spec/1.0`（Pydantic，`extra='forbid'`）。
适配代码在 [src/chenxin.py](src/chenxin.py)，实测数据与命令见
`tools/run_chenxin_specs.py`。

### 11.1 字段对应

| 他们的字段 | 本阶段使用方式 |
| --- | --- |
| `selection_items[].catalog_mapping.leaf_codes` | 候选类别；按这组类别逐个召回再合并 |
| `circuit_quantity` / `component_quantity` | 数量（物理用量未知时退回电路数量） |
| `constraints[]` | 能数值比较的转硬性条件，其余作偏好或仅说明 |
| `specified_references` / `preferred_references` / `reference_only` | 分别对应必须使用 / 优先考虑 / 仅作参考 |
| `requirement_ids` + `requirements[].source_quote` | 追溯链条：用户原话 → 需求 → 器件 |

### 11.2 转换时必须守住的一条

他们的 `constraints` **大多数不是工程判定条件**。实测 621 条约束里
483 条 `kind=user_device_description`，是"用户这么说"的溯源记录；只有 59 条
`design_requirement` 才是设计约束，而且数值常写在 `text` 里而不是
`minimum`/`maximum`。把描述性记录当硬性条件，会让每个候选都判成"未知"。
所以只转真约束，其余如实记为说明 —— 实测 528 个选型项里只转出 59 条工程条件。

### 11.3 结果写回

`apply_result` 把选定器件**追加**成新的 `device_references` 并挂到对应选型项的
`specified_references` 上，不改动他们原有的任何字段。这样他们的
`handoff.generation_adapter` 无需修改就能把选定器件投影成网表生成入口的输入。

写回有一条硬约束：他们的契约要求每条器件引用都能指回一句用户原话
（`source_quote` 必须逐字出现在对应 source message 里）。我选出的器件不是用户
说的，所以引用的来源挂在**它服务的那条需求**的原话上，链条是
「用户原话 → 需求 → 目录召回 → 用户确认」。

### 11.4 实测结果

用 46 份真实 RequirementSpec（528 个选型项）跑接口回归：

| 指标 | 结果 |
| --- | --- |
| 选型项 | 528 |
| **经过参数核对并有推荐** | **276（52.3%）** |
| 未核对（没有可判定的条件） | 246 |
| 阻塞 | 252 |
| 转出的工程条件 | 538 条（另有 83 条纯描述记录仅作说明） |
| 写回后通过他们契约校验 | 46 / 46 |

这个数字走了一段弯路，都记在这里免得再踩：

1. 最早记的是 **525 / 528（99.4%）**——那时只要召回到候选就标「推荐」，
   哪怕一条条件都没判过，属于假绿。
2. 修掉「未核对」口径后变成 **39 / 528（7.4%）**，这才是当时真实水平。
3. 后来又发现**是我自己的转换器太保守**：工作台其实把字段名、关系、单位都抽对了，
   数字只是写在 `text` 里而不是 `minimum`/`maximum`；而早期我按
   `kind == 'user_device_description'` 一刀切，把 562 条里 97 条可用约束全丢了。
   改成**按"有没有可比较的取值"判断**后，工程条件从 59 条涨到 538 条，
   覆盖率升到 **52.3%**。

**所以瓶颈不在工作台，在我这边。** 现在的做法是：不依赖 `kind` 标签，
只要字段名合法、关系词可映射、`text` 里能解析出带单位的量，就转成判定条件。

### 11.6 器件身份的二次复核

上游给的 `resolution_status` **不直接采信**。实测有把 `FMMT593`、`AO3401A`
标成「已定位目录身份」、但器件库里根本没有这两个型号的情况；盲目沿用会让我这边
跟着用错身份。

转换时对每个器件身份做一次复核，结论记在 `identity_verdict` 里：

| 结论 | 含义 | 处理 |
| --- | --- | --- |
| `confirmed` | 上游给的身份在目录里确实存在 | 直接用 |
| `corrected` | 上游给的身份查不到，但原文写法精确存在 | 改用原文写法 |
| `unresolved` | 两边都查不到 | 保留原文写法，标未确认，交给类别召回兜底 |
| `absent` | 既没有身份也没有原文写法 | 跳过 |

**复核只用精确匹配，不做前缀解析。** 这条是踩坑踩出来的：上游标「系列约束，
型号待选」时给的是系列名（`RT9013`），一开始我拿前缀把它钉成了 `RT9013-33GB`，
召回从"一批同类"缩成"一个"，那个型号又恰好不满足条件，整个选型项就被卡死了。
系列名本来就该原样保留，交给召回层按类别铺开。

这一步同时消除了上游的一处不一致：同一型号在不同项目里被标成不同状态时，
我这边只看型号本身，结论天然一致。

### 11.5 端到端串联（`tools/bridge_studio.py`）

已经把两边串成一条链，命令：

```bash
python3 tools/bridge_studio.py health          # 工作台是否可用
python3 tools/bridge_studio.py list            # 列出项目
python3 tools/bridge_studio.py run --project <project_id>
```

链路走向：

```
工作台 HTTP（[::1]:8878）
  └─ handoff-check → handoff → 下载 ZIP → requirement-spec.json
       └─ 本阶段：转换 → 召回 → 判定 → 用户确认
            └─ apply_result 写回 spec（追加 device_references）
                 └─ 工作台自己的 generation_adapter → pcbagent.netlist_input.v1
```

最后一步直接调用**他们的** `backend.handoff.generation_adapter`（需要能读到
`/share/home/chenxin/work/01_PCBAgent`），用的是他们的下游契约实现，不是另写一份。

实测两例：

| 项目 | 选型项 | 已核对并推荐 | 未核对 | 下游结果 |
| --- | --- | --- | --- | --- |
| CASE-09 PN532 NFC 调试器 | 5 | 0 | 5 | 已准备 1 个模块，4 项待选型 |
| CASE-05 Klipper 九轴主板 | 20 | 4 | 16 | 已准备 12 个模块，8 项待选型 |

产物在 `output/bridge/<project>/`：`requirement-spec.in.json`、
`candidate-set.json`、`requirement-spec.out.json`、`generation-input.json`、`report.json`。

**这两个结果暴露了当前最大的瓶颈**：上游 528 个选型项里只有 59 项带得出工程判定
条件，其余全是"用户这么说"的描述性记录。没有判定条件时，候选只是按类别召回，
从未做过参数核对——这种项现在会明确标成**「未核对」**而不是「推荐」，也不会被
自动确认送进下游。

## 12. 数据手册库（Milvus）

结构化参数表里 **65% 的关键参数**（36157 / 55646）是 `EXPECTED_BUT_MISSING`，
但这些值往往就写在数据手册正文里。本阶段已接入手册库把它们补回来。

### 12.1 连接方式

代码在 [src/milvus.py](src/milvus.py) 与 [src/datasheet.py](src/datasheet.py)，
用 Milvus 的 REST 接口，本机**不需要装 pymilvus**。参数与 chenxin 的实现保持一致：

| 项 | 值 |
| --- | --- |
| 地址 | `PCBAGENT_MILVUS_URL`，默认 `http://127.0.0.1:19530` |
| 库 | `DataSheetBaseV2`（12848 条）→ 回退 `DataSheetBase`（669212 条） |
| 集合 | `DataSheet`，按 `lichuang_id`（立创 C 编号）过滤 |
| 检索 | 标量过滤 + `content_sparse_vector` 的 BM25 稀疏检索 |

两个库覆盖不同：不少器件只在旧库里（LM358 的 C5252902、AMS1117 的 C347222），
所以必须按 V2 → Base 回退，不能只用 V2。

### 12.2 取值的纪律

手册是散文，取值比结构化表危险得多，所以设了三道闸：

1. **必须带单位**——否则 `LM358` 会被当成 358 这个"参数值"；
2. **单位必须落在该字段期望的单位族里**——否则 AMS1117 那句"输出电压……通过一个
   22µF 的电容"会把 22µF 当成输出电压；
3. **必须带原文引用与出处页**，结论里写明来自哪一页手册，与结构化参数表的来源
   分开标注（证据状态记作 `DATASHEET`，不混进 `PROVEN`）。

### 12.3 实测效果

抽样 120 组"结构化表里缺失的关键参数"：

| 结果 | 数量 |
| --- | --- |
| 从手册补到可解析的值 | 42（35%） |
| 手册里有该器件但没这个参数 | 60 |
| 器件没有立创编号，无法定位手册 | 18 |

第一版只补到 3.75%，原因是**检索回来的片段太少**（只取 BM25 前 6 段），放宽到 24 段
后升到 35%——说明主要瓶颈是召回，不是手册里没有数据。

补到的值会带着引用参与判定，例如 AMS1117 的 `dropout_voltage` 在结构化表里缺失，
手册里读到"the typical dropout voltage is only 1.2V at 1A"，于是
`dropout_voltage <= 1.5V` 这条判成满足，并注明来源页。

## 13. 大模型辅助（可选，非核心）

配置文件 `workspace/PCB_UI/llm.local.env`（`QWEN_BASE_URL` / `QWEN_API_KEY` /
`QWEN_MODEL`，当前为 `qwen3.7-flash`）。用 `DEVICE_SELECTION_LLM=off` 可整体关闭。

**它只做一件事：把用户的话翻译成结构化条件。** 调用顺序是
**规则 → 大模型 → 兜底摘要**：规则能识别的句子轮不到它，规则接不住才找它，
它给不出合规结果就退回摘要——宁可答不上来，也不猜。

它的输出必须过白名单：字段名、比较符、取值、选型项编号任何一项不合规，整条丢弃。
**检索和判定永远不由它做**：它不能产出器件型号，不能判定满足与否，不能碰数据库。

实测：规则路径 0.05 秒；大模型路径单次 24~46 秒，所以只适合兜底，不适合当主路径。

## 15. 界面上的项目工作区

不用再敲终端。界面左边栏直接列出**需求分析工作台里的全部项目**，点一下就把该项目
的最新交接包取回来——但**不自动跑选型**，选型由运行条上的按钮显式触发。

### 15.1 交互

| 操作 | 行为 |
| --- | --- |
| 点左栏某个项目 | **只取交接包并转换**，状态变「尚未选型」；已跑过的直接读缓存 |
| 按运行条的「开始选型」 | 这时才真正执行选型；跑过的按钮变成「重新选型」 |
| 项目分组 | 「已载入 / 等待上游 / 失败 / 未处理 / 示例」五组，**每组可折叠**，组标题带数量 |

| 点「内置示例清单」 | 不需要工作台也能看效果 |

| 状态 | 含义 |

位置在顶栏「导出」右边，点击打开 `http://<主机名>:8899/?project=<项目编号>`。
