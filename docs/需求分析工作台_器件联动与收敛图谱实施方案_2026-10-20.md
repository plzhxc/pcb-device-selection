# 器件修改联动与收敛图谱

目标：用户在画布修改器件或继续讨论后，器件清单、规范说明书、模块、接口、关系图和交接内容按同一份最新数据更新。收敛路径保留现有决定与依据，增加三张可切换、可操作的关系图。

## 1. 已有能力与本轮缺口

已有器件使用意图、目录身份、关联需求和模块、实际资料查询、版本保存、队列、AI分析及三视图。当前画布操作会保存器件引用并启动分析，但缺少明确的变更影响任务和整体同步门槛。原参考BOM只呈现上传文件内的器件，换成参考之外的型号后，本版采用清单不能继续只靠原参考表表达。

本轮以“客户修改一次，助手处理关联内容”为流程，不要求客户在每张图或每个章节重复修改。更换型号不推定新器件继承旧器件的电气能力。

## 2. 用户经过的流程

1. 在器件卡片点击“修改器件”，修改型号、用量、使用意图或用途，提交后收起并显示受理状态。可直接使用已知型号，也可结合真实目录继续核对。
2. 服务端记录修改前后、来源和实际关联的需求/模块/接口/条款，取消旧审核，将这些内容标为待同步。排队中的修改有回执，不会假装已进入正文。
3. AI核对相关功能、供电、接口、模块、参数和验收。产品目标继续保留；真实冲突才问客户。仅讨论比较、未决定更换时，当前方案保持原意图。
4. AI保存统一的新版本。已给目标继续有效的条目明确复核，过时文字实际修改；未清理的旧型号约束、关联复核或交接检查会阻止再次审核。
5. 本版器件表显示当前方案；原参考表继续保留原文件、原型号和观测数量。新器件不伪造参考位号、采购号或验证结论。

修改型号时清除旧目录身份、旧采购提示和不再适用的器件介绍；产品真实设计要求继续作为选型约束。保留原参考文件与历史版本，避免把换型解释成改写参考原图。

## 3. 三张图分别回答什么

| 图 | 客户要看清的问题 | 实际依据 |
| --- | --- | --- |
| 方案关系 | 每项需求由哪些模块承接，采用/候选器件在哪里？ | 当前REQ、MOD、器件引用及其真实关联 |
| 变更影响 | 刚修改的器件，影响了哪些需求、模块、接口与条款？哪些仍在同步？ | 变更记录、修改前后、实际依赖与当前复核状态 |
| 收敛检查 | 还差客户决定、AI整理，还是已经交给工程实现？ | 现有审核门槛、问题、关联复核、四项交接检查和工程待办 |

颜色和文字状态同时表达“已明确、待客户、AI同步、工程承接、仅参考”。图可以缩放、平移、拖动节点、全屏查看，节点可打开条目和依据。原有分主题决定卡片继续保留。

图的节点和连线由当前保存对象生成，不让模型另写一套容易过期的图。借鉴 [React Flow 官方的数据与连接更新说明](https://reactflow.dev/learn/advanced-use/computing-flows)所展示的数据驱动方式；本项目继续使用已有交互画布和 [Dagre 布局](https://github.com/dagrejs/dagre/wiki)，避免为这次小改替换整套图形组件。图是审核依据的呈现，最终是否可交接仍由真实审核规则决定。

## 4. 实现边界

- 同步任务只覆盖实际关联，不因同属一个总括章节而要求所有旧功能重新确认。
- 复用当前增量分析、来源校验和复核字段；不另建会与需求文档分叉的事实库。
- 客户可修改当前器件方案；目录身份选择继续只解决身份，不自动授权换型。
- 参数与资料未知交给工程任务；图谱里的“已明确”不等于电路验证通过。
- 旧项目无本轮变更时不批量回写，历史审核和报告保持原样。

## 5. 验证与交付

先补器件变更、局部影响、过期文字与审核门槛回归，再构建前端。以既有玩具和语音板验收案例的明确标注副本测试画布操作与简短讨论，保留真实AI过程；不会把这些副本说成从零重新完成的需求验收。检查文档、当前BOM、参考BOM、模块、图谱和交接的一致性，并测试未提交/提交中/失败恢复、刷新及手机布局。

使用隔离数据与8896端口开发。发布前两个服务需空闲，备份正式数据，核对旧127个项目的原记录不被覆盖；正式入口仍为8878。实际问题和调整写入后续验收记录。
