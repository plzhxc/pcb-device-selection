# 需求分析工作台：渐进引导与参考 BOM 优化验收

本轮依据《五案例真实用户压测与优化报告》优化现有工作台，以按键发声玩具、小智语音板两个案例检查：客户每次只补充少量信息，AI 持续整理需求、提出必要取舍、核对真实参考资料，最后输出可交接的需求说明书。

**本轮开发与两案例验收已完成，已更新到 8878 正式入口。** 两案均完成真实多轮问答、最终参考复审、模拟整体审核、交接包下载及现有流程入口读取。原有 125 个项目保持原样，追加本轮两个项目，共 127 个。最终正式需求验收仍由用户执行。

## 1. 本轮具体改进

| 原报告问题 | 本轮实现 | 验证范围 |
| --- | --- | --- |
| F-01 用户回答被排队内部任务阻挡 | 新输入可替换尚未启动的内部续跑；已经启动的任务完成保存后优先处理客户输入。问题尚未回答时，续跑先留 20 秒阅读窗口，不占推理槽位。 | 事务与竞态回归；实际逐轮输入、上传和回答记录。 |
| F-02 系统电压被误当器件额定能力 | 系统/网络提供的电压轨保留为产品目标；芯片额定能力仍与整板保证值区分。 | 原 Klipper 输入解析回归，没有重跑该案整个 AI 会话。 |
| F-03 关联复核过广 | 总括功能/流程/验收字段不再把共享该字段的所有需求都纳入语义复核；保留具体需求、模块和接口依赖。 | 依赖回归与两案实际版本更新；真实架构变化仍须复核。 |
| F-04 排队与实际分析混淆 | 显示真实排队、执行、保存及内部核对阶段；不编造进度百分比和预计完成时间。 | 两个真实模型会话；没有重新测量五并发极限或证明首问达到 60 秒。 |
| F-05/F-06 规范太长、重复全文 | 默认看本项目条款；完整专业规范可展开。每项需求保留一处正文，其他章节用短引用跳转。 | 唯一正文、完整字段和默认阅读的浏览器检查。 |
| F-07 接口补充负担过大 | 增加外部接口表，支持单行、单字段修改；提交收起，禁止重复提交，其他行沿用。 | 语音板真实修改一行；另外两行内容未变化。 |
| F-08 完成视图不明确 | 收敛页显示待客户决定、AI 整理和后续工程任务；保留真实变更记录与依据。 | 最终两案三视图、手机显示检查。 |
| F-09 能力链遗漏 | 交接需明确功能验收、能力链、供电接口、核心方案四项；有参考资料时增加最终真实模型复审。 | 两案复审及交接内容审阅；不等同电气验证。 |
| F-10 后续任务隐藏 | 在画布直接展示后续任务、负责人和完成条件，结构化交接一并携带。 | 交接包及实际输入适配。 |
| F-11/F-14 空结果、未运行的复核文案 | 无待决项明确表达完成；模块方案待采用时显示由客户操作，不错误地让客户一直等待 AI。 | 完成筛选与模块确认入口检查。 |
| F-12 频率字段和单位 | 区分射频、时钟、开关频率，显示数值和单位。 | 确定性回归；没有另跑 NFC 完整案例。 |
| F-13 目录候选难区分 | 候选展示采购号、封装、来源、记录和修订；详情关联当前器件引用。 | 候选展示及只读浏览器检查。 |

本轮还增加真实 ENET/BOM CSV 上传、原文件下载、参考全 BOM/本版核心方案分层、可追溯的采用按钮和用量来源。参考文件只表示已有设计，不能自动变成客户必须使用的器件，不能将观测数量直接冒充生产用量。

## 2. 两个案例怎样模拟普通客户

两案都从短句开始，逐个回答真实 AI 当轮提出的问题；没有把原始案例 TXT 或整理好的完整参数表一次灌入对话。参考 ENET 通过网页附件入口上传，采用方案通过网页按钮完成。浏览器脚本只负责输入、点击、截图和保存记录，不替模型生成答案，也不直接修改项目数据库。

| 案例 | 第一条输入 | 后续逐步明确的产品决定 |
| --- | --- | --- |
| 按键发声玩具 | 我想做个小玩具，按一下会播放声音，用电池供电。 | 播本机预录的同一段声音；先一个播放键；一节可更换的常见碱性 AA 电池，不充电；触摸只唤醒，再按播放键才发声；闲置省电。 |
| 小智语音板 | 想做一块能和我语音聊天的小板子，放桌上用，也能拿起来用。 | 联网语音聊天，直接连接 Wi-Fi；内置充电电池；普通 5V USB-C 充电，不快充；边充边聊、拔线用电池；约 2 小时连续聊天目标；配套外接小喇叭。 |

玩具是同类产品的简短输入变体，客户明确选择了一个播放键；不能宣称覆盖原 TXT 的六键版本。语音板也没有无依据增加原 TXT 中的全部性能数字、蓝牙功能或外设扩展要求。参考靠近程度应以真实功能、核心器件用途和用量逐项比较，不要求为了凑满采用率强加不需要的功能。

## 3. 参考资料怎样参与需求分析

玩具参考实际读出 22 个元件实例、14 行完整 BOM、5 行主要器件。原核心 CSV 的 4 行全部提取；额外的第 5 行是位号为 U9 的 XR0530-4R7M 电源电感，不是第五颗 IC。主要方案包括 CX588、C10S01X、PW5100、XR0530-4R7M 和 CS-1110-1*6。器件身份、低功耗/触摸能力和电气适配仍须用真实资料核验。

语音板参考实际读出 82 个实例、36 行完整 BOM、14 行核心分组。电池与喇叭两处 HC-1.25-2PWT 保留各自位号，分组数量为 2，不会合并成同一接口。型号、采购号、封装、参考数量、本版数量和本版用途分别保存。

语音板曾把 Flash 当成“客户没有要求录音”的可选件；固件启动存储是另一项基础运行前提。现在在最终复审中明确检查控制器完整型号和启动存储承接。ESP32-C3 系列不同变体的封装内/外 Flash 情况不同，不能只凭系列名称判断已解决存储。依据：[Espressif 官方 ESP32-C3 数据手册](https://documentation.espressif.com/esp32-c3_datasheet_en.html)。

另一个实际发现是，核心器件端点网名不同不能直接推出参考缺线。原网表中 MIC1 输出经 C1 耦合至 ES8311；ES8311 的输出经 C7/C8 及后续 RC 支路连接 NS4150B。模型上下文现在提供真实无源两端连接和位号归属，供其复核，而不是只给直接同网摘要。拓扑可追溯仍不表示偏置、波形、稳定性或电气能力已验证。

## 4. 开发中保留的失败及修正

- 语音板一次真实分析先生成重复接口汇总，修复输出又被过严的器件来源规则拒绝。已区分“器件身份来源”和“本次用途关联来源”，不同接口的汇总可合并，同端点矛盾仍拒绝；随后从 UI 重试，真实调用成功。
- 玩具采用核心方案后，一次真实分析更新维护接口时省略已有检查点的需求关联，导致整轮失败。现在稳定检查点可继承仍有效的原有关联；无来源、无旧关联或已删除需求仍拒绝。随后从 UI 重试，真实调用成功。
- 玩具模块采用后的内部整理出现一次 10 分钟超时。已保存版本没有丢失，失败及从 UI 重试的过程保留。超时不能算作已完成，也不能改写为零失败。
- 多个接口复用一个规范字段时，真实模型输出再次出现字段重复并进入自动修复。现在前置指引要求每字段一次，修复反馈列出具体重复 ID；没有为了通过而合并不同状态或掩盖同端点冲突。
- 玩具客户补充“尽量简单、能合用就合用”后，独立存储变为条件候选。模块采用文案补充适用条件，明确功能模块数不等于芯片数，不再让采用动作读起来像强制增加独立芯片。
- 完成卡原来的“12/14”容易让客户误以为还有两项没完成。现改为采用项数，并分别说明参考提取数、待采用建议和仅作参考数；有理由不用的参考器件不再表现为进度缺口。
- 浏览器工具在隔离服务启动窗口遇到过连接拒绝，记录未删除；后续操作先确认服务健康。该项与网页 JavaScript 错误、AI 分析错误分别统计。

离线原始失败输出重放只用于验证修复，不当作真实 UI 成功记录。两案开发过程经过多个修复版本，最终还须检查当前版本页面、说明书、导出与交接合同的一致性。
