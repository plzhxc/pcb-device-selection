# 需求分析工作台：第一阶段实现方案

日期：2026-10-15。实现目录：`../requirements_studio/`。总体依据：[调研与目标总览](需求分析工作台_调研与目标总览.md)。

## 1. 本阶段交付与解耦边界

交付可实际使用的本地需求文档工作台，具备真实 Codex CLI 问答、问题卡片、需求条目增量更新、三种图形、文档编辑、持久化和导出。

独立 FastAPI 服务、独立 Vite/React 前端、独立 SQLite 数据目录。不得导入 `netlist_end_to_end`、`agent_framework`、`web_console` 业务模块；不得触发网表、选型、数据库召回、模块分解等主流程。复用现有 Python 环境属于部署复用，不构成业务耦合。

模型固定：产品显示 `gpt6-luna-xhigh`；CLI 参数 `-m gpt-6-luna -c model_reasoning_effort="xhigh"`。接口不接受来自浏览器的模型、命令或工作目录覆盖。

## 2. 界面研究与设计决策（开发前）

| 官方参考 | 观察和可借鉴结构 | 本项目落地 |
| --- | --- | --- |
| Codex / ChatGPT 官方功能、更新记录 | 项目侧栏、连续对话、固定输入区、侧边成果区、简洁层次 | 低对比三栏工作台、对话为主操作入口、右侧为持续文档 |
| Codex App Server 用户输入 | 问题有明确请求/回答状态 | 内联问题卡片与自由输入，完成后保留记录 |
| OpenCode Web 与 question 文档 | Web 会话、结构化选项、自由回答、取消 | 独立网页入口、明确运行/失败/取消状态 |

官方资料支持结构和交互方向；字号、颜色、尺寸为本项目的设计选择，不声称逐像素复刻某个版本。

视觉：浅暖灰侧栏、白色会话、淡灰画布、白色文档，单一绿色强调色。正文约 14px，文档主标题约 24px。边框与留白建立层次；图标使用 lucide。按钮必须有实际作用和可访问名称。

桌面：侧栏 220px，可收起；对话宽度约 480px，分隔条可拖动/键盘调整；画布占据剩余空间。窄屏通过“对话/画布”切换，侧栏以抽屉打开。支持键盘操作、焦点提示和减少动态效果偏好。

## 3. 页面状态与操作

- 空白项目：提示用户描述想法，提供可填入输入框的例句，以及明确标注的示例项目入口。
- 已有需求：会话历史、文档标题/摘要、需求统计、图形与关键问题。
- 分析中：显示真实运行状态和耗时，允许停止；请求不会因切换项目而消失。
- 完成：展示 AI 回复、当前问题、本轮更新与版本。
- 失败/取消：保留已有需求和用户输入，提供重试或继续输入。
- 手动编辑：弹窗编辑需求条目、记录用户编辑来源、生成新版本。
- 版本查看：在变更列表查看版本和修改摘要。
- 导出：下载 Markdown 与 JSON，内容来自同一份已保存数据。

右侧“总览 / 说明书 / 变更”。图形选择“思维导图 / 功能框架 / 工作流程”；可缩放，节点关联需求。画布目录与需求表用于定位和发起针对性讨论。

## 4. 需求数据与文档

需求条目采用六类固定分类：项目概述、功能需求、性能指标、生产与测试、功能框架、器件与约束。正文另按 V3 第 1～5 章的 50 个小节补齐适用范围、已知要求和设计阶段边界；第 6 章实际器件选型保留给审核后流程。

每条需求包含稳定 ID、章节分类、名称、值、单位、优先级、状态、来源消息/原话。状态包括用户已提出、AI 建议、待确认、冲突和不适用。

模型输出结构化修改：回复、标题/摘要、需求更新、删除项、本轮问题增量、已解决问题、独立续分析任务、章节覆盖、流程草案和修改摘要。已有条目保留 ID，新条目由服务端分配 ID。用户事实要求原话可在所引用的历史用户消息中找到，否则降为建议；这属于保守来源检查，不能替代完整语义证明。

问题不随每轮整体替换。未回答的旧分支持久保留，回答一个只关闭实际得到答案的问题；暂缓、不知道及没有返回的旧问题均不能自动当作解决。前端每次最多集中呈现少量卡片，支持分支筛选和展开，回答草稿独立保存。

修改需求后，关联章节先重新核对。来源刷新且语义内容相同不导致覆盖失效；需要重新核对的已知内容由后台完成，不转化成让用户重答产品名称等旧事实。只有复核后确实缺少新决定时才提问，复核期间不能标记终稿通过。

终稿门槛由服务计算：50 小节均为有依据的已明确/明确不适用/明确委托设计阶段确定；不存在建议待确认、冲突或其他未决需求；没有待答问题；具备流程草案。达到门槛只进入待审核，用户确认才标记已审核，后续内容修改会重新核对。

完整说明书由服务端从需求条目确定性渲染，包含版本、来源、待确认项和流程。思维导图按同一分类和条目生成，功能框架关联需求，工作流程保留草案标记。框架图不代表已验证的器件引脚或电气连接。

## 5. Codex CLI 最小适配

参考文件：`../../../jlctest/01_PCBAgent/tools/codex_requirement_runner.py`。

每轮以独立、临时 Codex 调用执行，传入当前需求版本、历史对话和本轮输入，用 `--output-schema` 约束输出，使用 `--json` 获取真实阶段事件。由业务数据库持久化连续会话，避免绑定 CLI 内部会话格式。

执行固定 argv，不通过 shell 拼接；只读 sandbox；忽略用户配置但保留现有登录；独立工作目录；提示禁止调用 Codex 文件、命令或联网工具；检测到工具执行则拒绝结果。只转发产品所需的状态，不向用户展示模型内部推理或原始 CLI 诊断。

本阶段 CLI 通常在最终消息返回结构化结果，因此提供真实阶段状态及逐轮增量文档更新；不把最终 JSON 人工切片伪装为 token 流。

## 6. 持久化、并发与恢复

SQLite 保存项目、消息、文档版本、问题待办与历史、章节覆盖、补充队列、运行及运行事件。文档提交和版本记录在同一事务内完成。修改携带基线版本；版本不一致返回 409。一个项目同时最多一个分析任务，CLI 同时最多运行两个；重复请求使用持久请求 ID 去重。

分析期间继续发送会进入最多 20 条的可见队列，不提前混入当前模型上下文；当前轮次成功后顺序处理，优先于独立续分析。停止/失败后队列暂停保留，由用户恢复。补充携带发送时的轮次 ID，解决“先发送补充、停止请求先到达”的竞态。没有排队输入且模型提出可执行独立任务时，每个用户轮次最多自动继续一次；完成后等待答案，不关闭会话。

运行由独立任务驱动，SSE 只订阅事件；断开浏览器不会丢失运行。重新进入查询 active_run 并恢复订阅。停止终止本轮子进程组，保留上个文档版本。服务重启将遗留 queued/running 任务标记中断，允许重试。

默认仅绑定 IPv6 本机 `::1:8878`，使用 SSH 转发即可查看。当前为单用户本地工具，不包含公网账户系统或多用户权限管理。

## 8. 开发与打磨顺序

1. 保存总览和实施方案，核对 CLI 参数与环境。
2. 建立独立服务和数据契约，先验证真实模型调用。
3. 实现工作台与完整空态/示例，浏览器查看桌面与窄屏布局。
4. 接通发送、问题回答、保存、编辑、图形和导出。
5. 针对实际截图与交互检查调整间距、滚动、按钮和图形布局。
6. 验证真实两轮需求补充、来源保留、错误/停止/刷新、并发版本和导出。
7. 更新使用说明及验收证据，交付访问地址。

## 9. 验收标准

- 前端类型检查与生产构建通过。
- 本地服务页面和健康检查可访问。
- 使用真实 gpt-6-luna/xhigh 完成至少两轮需求提取与补充，保留前轮事实。
- 需求文档、表格、思维导图/框架引用同一条目；工作流程显式为草案。
- 项目切换、刷新恢复、手动编辑、问题回答、MD/JSON 导出可操作。
- 取消、失败和版本冲突不破坏已保存文档。
- 桌面、常见笔记本及手机宽度无整页横向溢出；控制台无未处理异常。
- 交付实际截图、检查结果、运行命令及明确后续范围。
