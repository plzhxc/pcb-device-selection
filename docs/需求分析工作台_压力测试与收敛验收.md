# 需求工作台压力测试与完整收敛验收

日期：2026-10-15。验收对象：`requirements_studio` 独立需求工作台。用户补充目标：多轮完成整份需求说明书，未答问题不能让会话终止或被其他分支覆盖。

## 1. 验收方法与完成条件

每项对外功能至少在两个独立项目/浏览器轮次中操作。按真实操作顺序点击、选项选择、输入、粘贴、修改、切换、停止和刷新；服务端检查作为补充。验收数据与正式数据库隔离，不将测试问题或虚构产品写入用户项目。

采用两类运行环境：

- 真实 Codex CLI，固定 `gpt-6-luna` / `xhigh`，检查需求语义、多轮补充、来源、V3 收敛和用户审核。
- 明确标记为 `controlled_cli_fixture` 的 CLI 测试替身，执行重复浏览器功能、故障注入和批量负载。测试收据单独标记 `real_inference: false`，不能当作真实模型证据。

浏览器为本机 Chromium 126，使用独立用户目录；页面来自实际 React 生产构建。覆盖桌面、笔记本、平板、390px 与 320px 手机宽度。

完成条件分为三层：

1. **一轮分析完成**：本次修改校验通过并保存新版本。
2. **需求收敛待审核**：V3 第 1～5 章 50 小节全部核对，所有适用字段有明确需求或有依据的不适用/设计阶段边界；无未答问题、无待确认建议或冲突需求，具备流程草案。
3. **本版已审核**：达到第二层后，用户阅读并点击确认。AI 不能自行审核；内容修改会使旧版审核失效。

第 6 章实际器件选型按原 V3 规范在审核后进行。需求终稿记录的是需要达到的目标，不能声称电路、器件参数或硬件测试已经验证。

## 2. Codex 交互参照与本次实现

官方资料区分 Queue（当前轮完成后继续）和 Steer（引导当前工作），并提供持久线程和用户输入生命周期。本项目继续使用用户指定的 Codex CLI，采用应用层持久会话、队列和问题待办；本次未迁移至 App Server。

参考：[Codex Queue / Steer 与工作流](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)、[Codex App Server](https://learn.chatgpt.com/docs/app-server)。视觉采用项目侧栏、中心对话、固定输入区与侧边成果，保持中性正文和少量强调色；右侧需求画布为本产品的领域功能。

每轮最多新增 3 个问题，只限制本轮呈现数量。旧问题、暂缓问题和不同分支持久保留，可筛选或展开。等待答案没有会话超时；有明确的独立任务时最多自动续分析一次/用户轮次，用户排队补充优先。独立工作完成后显示等待补充，不伪装持续运行。

## 3. 发现的问题及修复

| 问题 | 用户影响 | 修复与回归 |
| --- | --- | --- |
| 问题列表整体替换 | 新分支可能覆盖未答旧问题 | 增量问题待办、已解决问题归档、延迟回答与部分回答回归 |
| 分析中隐藏问题、无法发送补充 | 无法一边等待一边补充其他内容 | 保留可交互卡片，提供持久补充队列，顺序处理 |
| 问题答案仅保存在组件内 | 刷新或文档新版本可能清空未提交回答 | 按项目/问题保存选项与文字草稿，组件不随版本重建 |
| 提交问题回答会清空独立输入草稿 | 另一条尚未发送的想法丢失 | 分离问题提交与输入框发送，保留其他草稿 |
| 回答卡片不等于真正回答问题 | “没想好”可能被机械当作已解决 | 不因点击提交自动归档，结合模型解析；明确暂缓保持待答 |
| 停止与补充请求倒序到达 | 刚停止便又启动补充，违背用户意图 | 补充关联发送时轮次；停止先到则补充暂停留在队列 |
| 过期读取覆盖新任务状态 | 页面可能短暂退回旧版本或旧运行 | 文档/运行单向更新，写入后使过期读取失效；延迟响应注入复测 |
| 补充验收细节后反复询问已知内容 | 关联章节失效可能被错误转成重复提问，收敛反复 | 区分语义修改与来源刷新；由后台复核关联小节，真正缺少新决定才提问 |
| 服务停止被长期 SSE 阻塞 | 重启可能等到整个模型轮次结束 | 限定服务优雅关闭等待，随后中断当前子进程；两轮真实停启复测 |
| 丢失发送响应后重试 | 可能重复创建消息和模型调用 | 浏览器持久请求 ID，与服务端幂等配合 |
| 无问题被误解为完成 | 三问后可能过早结束整份说明书 | 50 小节覆盖、未决项、流程和用户审核门槛；缺口仍在时继续提问 |
| 问题分类标签被浮动标题挤成竖排 | 卡片阅读困难 | 清理浮动布局，增加文字对比与边距，多尺寸复测 |
| 审核后画布页眉仍写“草稿” | 用户无法判断当前版本是否审核 | 顶部与正文统一使用同一审核状态，两轮复测 |
| 旧示例问题没有分支字段 | 精度问题被显示为项目概述 | 从关联需求继承分类，正式旧项目只读两轮验证 |

之前 Android 回答的 `phone_platform` 混入需求删除列表问题，保留回归覆盖；真实需求取消与未知编号仍分别校验。

## 5. 已完成的负载与浏览器结果

- 基础浏览器：40 项 × 2 轮通过。
- 扩展交互：48 项 × 2 轮通过，包括关联章节自动复核，不要求用户重答已知事实。300 项需求页面切换及渲染约 908 / 445 ms。
- 网络与过期读取：9 项 × 2 轮通过；断网和故意丢弃响应造成的网络错误单独记录，未出现页面程序异常。
- 服务停启：7 项 × 2 轮通过，包括在实际子进程运行和队列有内容时关闭并重启服务。
- 键盘与抽屉操作：9 项 × 2 轮通过；审核显示及不重复提问：2 项 × 2 轮通过。
- 每轮 40 条同时补充：20 条接收、20 条明确返回容量限制；重复请求不重复排队。停止后恢复，20 个处理版本和输入逐条保存。
- 每轮 240 次读取，并发 12：第一轮 P95 1446.2 ms / 最大 1781.6 ms；第二轮 P95 679.0 ms / 最大 709.7 ms。数字包含本机受控验收负载，不代表公网性能。
- 每轮 12 个独立项目完成；后台同时运行 CLI 的观测峰值为 2；没有 HTTP 500。

核心检查最终为 45 项 × 2 轮通过，包含来源、问题生命周期、不同分支相同问法、覆盖失效与自动复核、版本、队列竞态、生成日期恢复、真实子进程取消和超时。机器输出见 `unit-round-1.log`、`unit-round-2.log`。

上述功能浏览器断言连同真实模型的 11 项 × 2 轮，共 252 次通过；它们是两轮功能断言次数，不代表 252 项互不重复的功能。正式入口另有 11 项 × 2 轮、共 22 次只读检查通过，结果见 `production-ui.json`。测试替身不作为真实模型语义证据。

## 6. 真实模型完整收敛

使用两份明确标注为虚构的产品负责人规格，覆盖 50 个 V3 小节及设计阶段边界。通过真实页面输入模糊想法、只回答一个问题、分析中补充其他分支、粘贴完整规格、继续回答验收方法与保护边界，达到可审核后点击确认，再修改旧预算并检查审核失效。

| 真实案例 | 用户输入轮次 | 收敛需求数 | 收敛版本 / 审核版本 | 结果 |
| --- | --- | --- | --- | --- |
| 办公室桌面温度显示器 | 6 | 30 | v6 / v7 | 50/50，零未答问题、零未确认需求；修改预算后旧审核失效 |
| 第二套独立桌面温度显示器规格 | 9 | 38 | v10 / v11 | 50/50，零未答问题、零未确认需求；修改预算后旧审核失效 |

第一套从 48/50 小节继续回答显示可读性与异常注入验收问题，才达到完整收敛。第二套真实后台续分析在用户回答前新增了观看距离分支，旧问题仍保留；不是每次用户说完就结束分析。

第二套还遇到了真实范围矛盾：笼统的“全部交给设计阶段决定”与此前“无电池、不充电”存在歧义。系统保留冲突并拒绝审核；产品负责人明确范围后继续收敛。证据为 `real-scope-conflict.json` 和 `real-owner-clarification.json`。不能为了显示 50/50 而自动抹去矛盾或把所有字段机械标为不适用。

审核后的预算修改分别达到 v9、v12，两份当前文档经过关联小节复核，均恢复至 50/50 待审核、零待答问题、零待复核项；旧审核没有自动恢复。机器证据为 `real-convergence.json`、`real-final-state.json`，每套真实浏览器验收 11 项通过，页面程序异常为零。

两个曾经由用户动作审核的版本已从验收数据库原样导出，并注明为虚构测试产品：

- [样例 1：30 项需求、v7 已审核](需求分析验收样例1_已审核.md)
- [样例 2：38 项需求、v11 已审核](需求分析验收样例2_已审核.md)

每份包含 V3 的 50 个小节、结论与用户依据、需求条目、流程/架构 Mermaid、变更记录。这里“已审核”表示需求范围已由模拟产品负责人确认，实际器件、电路和硬件测试仍属于后续阶段。

多行规格采用原样粘贴并校验输入框全文一致，避免将换行模拟成 Enter 造成多次提交。早期脚本的换行模拟、浏览器自动化协议等待时间不足等问题保留在排错记录中，修正后重跑；这些操作均发生在独立验收数据中。真实模型长轮次允许等待，与后台 10 分钟调用上限对齐，用户页面仍可交互。

## 7. 复测入口

在独立验收服务及对应测试替身环境中执行。以下脚本不可直接指向正式数据目录：

```bash
cd requirements_studio
cd frontend
npm run build -- --outDir ../.runtime/ui-audit-dist
cd ..
../.venv/bin/python tests/serve_audit.py controlled
```

另一终端执行受控验收：

```bash
../.venv/bin/python tests/seed_ui_audit.py
REQUIREMENTS_STUDIO_DATA="$PWD/.runtime/unit-app" ../.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v
STUDIO_TEST_URL='http://[::1]:8881' STUDIO_TEST_PROVIDER=controlled_cli_fixture node tests/browser.mjs
node tests/interaction_audit.mjs
node tests/connectivity_audit.mjs
node tests/restart_audit.mjs
node tests/keyboard_audit.mjs
../.venv/bin/python tests/load_audit.py
```

真实验收单独启动 `tests/serve_audit.py real`，再执行：

```bash
../.venv/bin/python tests/real_audit_profile.py
node tests/real_convergence.mjs
```

`browser.mjs` 支持 `STUDIO_TEST_URL`、`STUDIO_TEST_OUTPUT`、`STUDIO_TEST_ASSETS`、`STUDIO_TEST_PROVIDER`，用于分离不同轮次的报告和截图。真实模型测试默认访问独立 `8880`，受控测试默认访问独立 `8881`；正式服务仍为 `8878`。

正式入口只读复测可执行 `node tests/production_smoke.mjs`；保存各项两轮证据后可执行 `../.venv/bin/python tests/summarize_audit.py` 重新校验并汇总。汇总脚本要求两轮记录齐全，不将中途中断的单轮结果视为全部通过。

## 8. 交付状态与边界

本次第一阶段验收通过：独立 UI、真实 Codex CLI、多轮问题收敛、持久草稿/队列、故障恢复、图形与文档联动、50 小节检查和用户审核已经落地。每轮 3 个新增问题是阅读和决策节奏，不是整个需求分析的上限。

正式入口 **http://[::1]:8878/** 已更新至所验收构建，旧前端资源保留以兼容已打开页面。发布前备份为 `requirements_studio/.runtime/backups/before-ui-acceptance-release-20261015T105122Z.sqlite3`。发布后逐个核对原有 3 个项目：文档原始内容哈希、版本与消息数量均与发布前一致。证据见 `production-before.json`、`production-release.json`、`release-assets.json`。

已有项目不会因为打开页面就自行消耗模型调用；刷新页面后可从现有版本点击“继续完善缺口”，或直接回答/补充。此前已确认的需求继续保留。

验收不等于对任何未来输入保证零错误。复杂电气语义的形式化验证、多人协作、公网部署、完整历史恢复、主流程 `RequirementSpec` 交接与第 6 章器件选型仍在后续范围。模型输出按轮次校验并保存，当前没有逐 token 生成文档正文；独立续分析每个用户轮次最多一次，有其他决定依赖时保持等待，不无限自问自答。

最后关闭验收服务时发现账户磁盘配额耗尽：文件扩展返回操作系统错误 `122 / EDQUOT`，继而出现 `SQLITE_IOERR_SHMSIZE`，项目读取一度返回 500。文件系统整体仍有空间，因此不能只凭 `df` 判断账户可写。仅清理本次生成的 10 个 Chromium 临时用户目录（约 180 MiB）后，1 MiB 写入/同步、三个数据库完整性检查、正式项目读取与原文哈希复核均恢复通过。没有删除数据库、截图、模型收据或验收报告。正式只读浏览器脚本现会在结束后清理其临时用户目录；恢复后再执行两轮正式入口检查。详细记录见 `storage-recovery.json`。本次没有修改 SQLite 日志模式或用旧备份覆盖当前数据。

最终机器汇总为 `requirements_studio/.runtime/verification/ui-audit/summary.json`。桌面/手机发布截图为同目录 `production-desktop-round-1.png`、`production-mobile-round-1.png`；两轮完整功能、网络、停启与真实模型证据均保存在该目录，历史失败记录未删除。
