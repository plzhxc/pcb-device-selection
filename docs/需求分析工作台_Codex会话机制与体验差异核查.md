# Codex 会话机制与交互体验核查

核查日期：2026-10-16。初次核查后端：`63041a1d480146c274409b917b60d470cb5076b17b2d1f3167264ad52ba3e55e`；当前后端为`89425993acf9d3f654d9fa3e79509aa4f575d36f81eb3d3c730b0858ea185d55`，会话与回复机制保持一致。本记录区分源码事实、官方公开能力与实际验收观察；本轮不修改回复风格、会话接入方式或提问呈现方式。

## 1. 对用户问题的直接回答

**当前不是一个工作台对话框对应一个持续存在的 Codex CLI 原生会话。**

- 工作台的每个项目独立保存对话、需求文档、问题、模块及器件资料。
- 隔离单位是项目，不是浏览器窗口。两个窗口打开同一个项目，会读取同一份记录；新建项目才有另一套独立业务记录。
- 每次需要新模型推理时启动新的 `codex exec --ephemeral` 进程；已取得合法结果的恢复场景可以复用该结果。进程结束即完成本次调用。当前没有保存并恢复某个原生 Codex thread/session ID，也没有执行 `codex exec resume`。
- 下一轮由工作台重新组合当前需求文档、最近 40 条消息、被文档引用的历史用户原话、问题回答、相关规范和器件证据，作为新调用的输入。
- 因此存在**独立的项目业务上下文**，但不是同一个 Codex 原生会话持续积累的上下文。模型权重不会因为一个项目的对话而单独改变。
- 工作台保留完整对话不代表每轮将全部历史逐字交给模型。没有进入文档、也没有被引用的较早细节，可能不在后续调用的输入中。

源码依据：`requirements_studio/backend/codex.py` 的 `_invoke_once()` 与 `_run()`；`backend/model_context.py` 的上下文整理。独立项目保存依据为 `backend/store.py`。

官方说明：非交互调用可以通过明确的会话 ID 恢复；`--ephemeral` 用于不保存该次原生会话记录。见 [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)。官方 App Server 提供独立 thread、turn、恢复与消息事件；见 [Codex App Server](https://learn.chatgpt.com/docs/app-server)。这是官方提供的能力，不表示本工作台已经使用这些接口。

## 2. 与官方 Codex 的体验差异：先记录，不直接改造

| 维度 | 当前工作台的实际实现 | 官方公开能力与对比意义 |
| --- | --- | --- |
| 连续会话 | 每轮独立调用，由工作台重建输入。 | 原生会话可恢复；App Server 可在同一 thread 中持续增加 turn。两种机制不能等同。 |
| 首次响应与过程反馈 | 有后端阶段提示及每 45 秒的等待提示；只有模型已经完成的非 JSON 文本才作为公开进展转发。 | App Server 提供消息增量事件。当前“有进度消息”不等于“已经逐字呈现 AI 的实时回复”。 |
| 最终回复 | 模型同时返回说明文字和大量结构化文档变更，后端校验成功后整体保存。 | 官方客户端可以持续呈现公开说明与工作事件；本工作台的可见更新更依赖整轮结果完成。 |
| 分析中的用户补充 | 工作台将补充放入队列，在后续分析中合并；没有把新输入直接交给正在运行的临时 CLI 进程。 | App Server 提供 turn 生命周期与 steering 等接口。排队追加与中途改变当前推理方向不是同一种能力。 |
| 用户暂不回答 | 未答分支持久保留；无需用户回答的内部整理最多续分析 3 次，并有重复任务停止规则。 | 这不是模型无限持续思考。应以“问题保留、独立事项可推进、回答后继续”向客户解释。 |
| 提问内容 | 面向硬件需求文档，受规范字段、模块、证据和输出契约约束。 | 官方 Codex 面向更通用的任务。模型相同也不保证语言、节奏和问题密度相同。 |
| 工具权限 | 禁止模型直接读文件、执行命令、联网和调用 Codex 工具；器件查询由工作台受控服务处理。 | 官方 Codex 可按环境权限调用工具。这是本产品的范围选择，不能为了外观相近就直接放开所有权限。 |
| 回复的自然程度 | 受本产品系统提示、结构化输出、校验修复及 UI 提问卡片共同影响。 | 不能仅凭“接入了 Codex CLI”就宣称使用感受等同官方客户端；具体问题需要用实际对话对照判断。 |

“像官方 Codex”需要分别考察：能否迅速回应、是否说明本轮在做什么、是否先使用已知信息、问题是否符合当前客户认知、是否给出必要建议、能否接住补充和修改，以及最后是否形成可用结果。先把可见事实记录清楚，再讨论产品设计，不凭主观印象整体重写提示词。

## 3. 本次真实用户验收约束

1. 原始 TXT 案例验证与普通客户简短输入验证分开，不能互相冒充覆盖结果。
2. 普通客户先描述用途，不主动输入芯片、内部电源轨、引脚或完整方案。
3. 每轮主要回答 AI 刚问的问题；不知道就直说，并观察 AI 是否能提出易懂建议与取舍。
4. 不用一次性“完整需求补充”、通用“全部确认”或测试脚本替 AI 完成模块分解。
5. 模块方案应由 AI 提出职责、类别与关系；模拟客户只按自己理解的产品功能审阅。
6. 不以界面显示“可审核”作为通过依据。还需读完整说明书，核对原始要求、对话决定、实际模块、器件意图、待办和验收条件。
7. 保留真实 UI 操作和对话；人工审阅后才点击审核，再通过 UI 导出交接包。
8. 两个案例形成完整过程后汇总问题；属于回复感受的差异仅记录，本轮不修改。

普通客户入口：主工作台项目名以“普通客户验收”开头。详细记录存于 `requirements_studio/.runtime/customer-acceptance/`，项目内容由工作台正常保存。

## 4. 当前观察

已启动按键发声玩具、NFC 读写调试板两条普通客户会话，第一条消息均未给出器件与内部电路方案。后续观察按真实结果追加，不预填通过结论。

### 已出现的具体体验差异

- 早期回复多以“已记录／已复核／仍待确认”汇报状态，而不是先直接帮助客户理解当前取舍。部分回复直接要求回答问题编号。
- NFC 客户问“各1路是否代表三块板”后，AI 能纠正板卡与功能模块的混淆，但继续使用“实例”等术语；日常用语仍可改进。本轮仅记录。
- 客户正在回答时，先前启动的内部核对仍可能先返回“问题待答”的说明。界面通过已收到回执和队列显示缓解误解；这与向同一活动 turn 追加新输入的机制不同。
- 普通客户 NFC 项目首度显示可审核时，正文已有功能和边界，但缺少足够直白的操作验收步骤。人工审阅要求 AI 补充，未直接点击批准。应将“按钮已可点”和“客户已看懂、能验收”分开检查。
- 玩具用户不懂续航时，AI 提出至少14天的样机目标并标为建议；客户确认后才成为要求。电池建议同样保留节数与功耗核验，这段引导符合预期。

- 已定位到一处确定的服务端改写：`backend/experience.py:review_reply()` 在审核门槛未满足、模型文字却提到可审阅时，会用固定的“本轮已整理／当前仍为草稿／下一步需要……”替换整段回复。它用于阻止虚假完成提示，但也会影响自然交流；因此不能把看到的每一句模板文字都归因于 Codex 模型原本的回复。该函数本轮未修改。
- 玩具客户回答完已提出的问题后，曾出现“没有待答问题、审核仍不可用、四个模块提案待确认”的状态。点击界面“继续完善缺口”后仍未直接给出面向客户的下一问。已由模拟客户自然追问“我不知道下一步做什么”，继续观察；此项保留为引导连续性问题，不能用用户未填工程细节解释。

- 另一处确认的服务端插入为 `backend/domain.py` 的缺口兜底问题。玩具新增验收建议后，模型本轮没有提问，后端生成了“请补充REQ-006、REQ-007”的问题。其编号不符合普通客户的理解习惯，应记录为系统生成的问题而非模型原始措辞；本轮同样未修改。客户通过正常输入框用日常语言接受声音与检查建议，继续验证能否收敛。


## 5. 本轮独立发现的调用兼容性故障

物联控制盒原始案例在v9内部整理时，上游严格结构化输出接口拒收了JSON Schema：部分对象的 `required` 未覆盖全部属性，数值约束的联合分支也只是局部条件。这是调用格式问题，不是用户要求不能收敛，也不是会话记忆丢失。

修复仅在CLI输出Schema的编译边界进行：补齐所有对象必需字段；可选值仍允许null；数值下界/上界用完整对象分支表达；重复枚举以引用共享，保留全部合法选择。历史记录的本地校验模型、提示词、提问方式、公开回复改写和会话机制保持不变。

官方依据：[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)。这里修复的是严格输出契约，并不将App Server或原生会话恢复视为已实现能力。

补丁后端指纹：`3da99f33604ec935fb8aa7be7ef9ff3fad307b70c740c3f8e3fe5370ff40f49f`。开发服务已真实重试成功，文档从v9继续到v10；189项回归通过后，确认主服务无活动分析，再发布主服务。原有64个项目数据库行指纹全部一致。原始失败及重试保留，不删除历史失败以制造通过率。


### 第二轮对话节奏观察

普通客户NFC第二轮的首次输入与第一轮相同，但本轮AI问了卡片类型、电脑工具、读写范围三个问题，选项与上轮并不逐字相同。验收允许这种差异，检查其是否帮助客户决定实际用途。

控制盒回答断网状态时，答案已由UI接收并进入队列，先前内部核对仍先返回“Q-006待决定”；随后新用户轮正常吸收答案并解决问题。不能将中间那条提示当成最终丢失答案，但它会让客户觉得AI没有听懂。该时序与原生同一活动turn的steering体验不同，保留记录不修改。

当前产品的系统提示要求reply简洁报告理解、本轮变化及下一步；这也是频繁出现“已记录/已整理”措辞的直接产品约束。模型还要在同次输出生成需求、模块、规范字段与来源变更，等待完成后才保存。因此即使所用模型相同，输出目的、流式呈现和会话生命周期不同，使用感受仍可能明显不同。
