# 需求分析工作台：体验修复与真实使用记录

日期：2026-10-15。本文对应用户反馈后的体验修订，优先于之前文档中“247字段必须全部闭合”的旧验收口径。

## 1. 这次要解决的实际问题

用户回答一个问题后，应该明确知道“回答已收到”，而不是继续面对可重复点击的选项。最终文档描述这一款产品，不应该把模块规范目录当作项目正文。用户需要决定产品用途、功能、体验和关键验收边界，工程人员负责进一步设计器件、连接、PCB与工艺。

保留原有中心对话、右侧画布、规范模块类别、字段与来源账本、版本和固定真实Codex CLI。调整呈现与收敛责任，不启动后续选型或原主流程。

## 2. 修复后的交互

### 回答生命周期

1. 点击提交时，立即把本次回答的选项收起，显示“正在提交”。这一步不等待HTTP响应。
2. 服务端接收后显示“已收到，正在分析”或“已排队”。其他未答问题仍可操作，普通输入框可继续补充。
3. 同一问题的回答正在运行或排队时，服务端拒绝换一个请求编号再提交的重复回答；同一请求编号的网络重试保持幂等。
4. 刷新从服务端恢复回执；不会重新把待处理回答显示为可选项。
5. 分析确认已解决的问题正常归档。仍需补充、失败或暂缓的回答保留记录，用户可以明确选择重试、修改或继续回答。
6. 网络提交失败会恢复选项并保留答案草稿。暂缓不清空未提交文字。移除排队回答只恢复对应问题。

用户修改已经提交的决定，可直接在对话中说“上一条改成……”。重复点击与真实修订是不同操作，后者仍正常受理。

### 用户默认看到什么

| 层级 | 内容 | 是否要求用户逐项回答 |
| --- | --- | --- |
| 产品决定（默认） | 用途、场景、功能、指标、实际约束、必要问题、下一步 | 仅确实需要产品取舍的问题 |
| 专业核对 | 当前产品与实际模块相关的实现内容、来源、待设计事项 | 可以讨论，不要求普通用户填写器件能力值 |
| 完整规范（参考） | V3完整目录，包括尚未采用的模块 | 不是项目待办或正文 |

默认不再展示一个必须刷满的247项进度问卷。工作名称或“消费/工业”等分类标签没有明确，不单独阻止审阅；确实影响安全或适用性的用途风险仍要澄清。

### 等待时能看到什么

页面显示真实的资料读取数量、本轮核对重点、CLI阶段、已用时间、等待状态，以及CLI公开输出的简短说明。阶段、时间和说明保存到对应用户消息下，可展开“查看本轮整理过程”；刷新后仍能查看。

这些内容是实际阶段与公开摘要，不是私有推理。结构化完整回复和画布修改在本轮通过来源、格式和版本校验后出现；当前没有逐字流式发布尚未校验的说明书。

### 实测发现后继续修正

真实番茄钟对话中，模型曾在模块仍为建议时声称“现可整体审核”。服务端现在会把这类与实际检查矛盾的完成宣称替换成真实修改和下一步；原始CLI输出保留在运行证据中。对话区增加模块成组确认入口，用户核对本组实际类别、用途和数量后确认，并明确把具体实现交给设计阶段，避免逐个进入专业编辑器。

另一轮模型拼接了两段不相邻的用户原话，自动复核仍未纠正，整轮被保护性拒绝。新增严格的原文恢复：只有按顺序匹配到同一消息中的完整真实分句时，恢复成包含中间内容的连续原文；改写、倒序、虚构、修改数字或删除否定词不恢复。恢复记录写入`validation.json`，真实引用仍需完全匹配原消息；恢复跨度超过3000字也拒绝。这里没有跳过证据检查或替用户补充确认。

温度显示器进一步暴露了旧自动缺口规则的问题：引用“USB-C 5V供电”就把功耗上限、法规要求和电压容差三个未知模板字段列为必答。现在只有核心决定、已明确的实际产品边界、此前已明确而待复核的决定及冲突进入该检查；单纯提及某个领域不创造新硬指标。真实待答问题和未明确REQ仍拦截审核。原先未知字段的变更复核保留原状态，不把它升级成用户已设定的约束。

界面同时补齐模块待确认数量，避免所有可见计数为0但审核按钮不可用。模块成组确认用语改为“满足此前已明确的产品要求”，不替没有预算要求的用户新增成本上限。B会话保留旧用语引出成本问题以及明确“无硬上限、低成本优先”的完整过程。

## 3. 项目说明书与规范目录的关系

Markdown正文按项目内容生成，包含实际需求、补充产品边界、实际模块及关系草案、工作流程、设计交接、待答问题和来源。

- 只列本版采用的模块实例，类别必须来自用户提供的模块规范。父类或子类按实现明确程度选择，不要求用户记编号。
- 未采用或已取消的模块不展开模板章节，也不留在模块关系图里。
- 用户明确提出的范围排除可以作为产品边界保留，例如“不联网”。这不等于展开所有无线模块及其参数。
- 字段账本中有真实项目结论、但没有另建重复REQ的内容仍进入说明书，防止只保留REQ表造成漏项。
- 未明确的技术参数不写成已确认、不凭空填数值，也不为了清空清单伪造用户授权。
- 完整247字段账本与规范目录继续保留于结构化数据和参考视图中。

## 4. 如何判断需求阶段可以审阅

代码检查核心用途、场景、功能名称、功能描述与指标，以及已有依据的其他产品决定；工作名与分类元数据不强制作为独立决定。实际需求不能有未明确、AI建议待确认或冲突状态；待答问题必须处理；必要硬件功能须有规范模块承接，方案不能停在未确认建议；须有工作流程并处理确定性冲突。

未知工程参数可以保持待设计。它们不会因文档可审阅就被改成“已确认”。模块类别、用途或结构发生变化仍需内部复核实际相关的框架和连接，不允许绕过影响检查直接批准。

这是需求文档审阅，不是电路或硬件测试通过。已审核必须由用户按钮确认；新需求修订会取消旧版审核状态。每轮少量问题不限制总轮数，未答分支持续保留。

## 6. 可重复验证与配套脚本

在`requirements_studio`目录运行：

```bash
../.venv/bin/python -X utf8 scripts/ux_dev.py check
```

脚本执行后端回归、独立前端构建，以及两个随机种子的浏览器流程；自动启动并关闭自己创建的8893服务。`unit`、`build`和`accept`可单独执行。受控CLI只用于可重复的延迟、失败、网络和交互检查，明确标记为非真实推理；不会接管正式8878的模型或修改正式用户项目。

浏览器每轮35项，验证提交前后状态、快速重复操作、跨分支排队、刷新、暂缓草稿、断网、失败重试、保存的阶段记录、产品与专业分层、仅实际模块的说明书、真实用户审核动作、模块方案成组确认及320/390/768/1440宽度。

验收数据位于`requirements_studio/.runtime/ux/verification/`，包括`unit.log`、`browser.json`、`browser.log`与截图。`scripts/ux_dev.py`不会自动在正式入口创建测试会话。

真实使用由`tests/ux_live.mjs`操作正常8878页面，逐轮根据实际问题决定下一步。它没有预先塞入完整规格，也不通过接口伪造模型回复或批准。动作、完整原始消息、模型输出和阶段记录都存入正常会话；具体结果见下方记录。
