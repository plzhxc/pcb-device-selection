# 需求分析工作台：第三阶段现状与数据源调研

调研日期：2026-10-16（北京时间）。性质：开发前核查。本文记录已观察到的事实、复用条件和缺口；第三阶段的待开发内容见[实施方案](需求分析工作台_第三阶段领域能力补齐实施方案.md)。

## 1. 对齐本次任务

整个产品要让用户从自然语言想法出发，通过多轮对话、必要的提问和持续更新的画布，形成经过用户审核、可追溯、可交给后续设计的需求说明书。

工作台当前仍是独立前置产品。第三阶段承担总览中已有的四项任务：**器件证据、引用意图、影响分析、完整交接**。这四项都服务于需求分析。完整的候选选型、最终选用和网表生成属于后续业务。

本轮完成文件和源码调查、正式服务只读巡检、数据库与 Milvus 的只读样本查询，并形成开发方案。没有调用真实模型，没有更改应用逻辑、项目需求或数据库业务数据，没有执行导入、发布、服务重启。

## 4. `dataS` 的实际形态和当前数据

调查路径：[dataS](/share/home/chenxin/Worklib/database/dataS)。重点阅读 README、FINAL_STATUS、数据库结构、PCBAgent 集成说明，以及 `db.py`、`query_service.py`、`priority_service.py`、`core_service.py`、`freshness_service.py`、`full_chain_service.py`。

它是一套**数据库查询、发布和追溯工程**。数据分为：源 MySQL 原始器件、发布 MySQL 视图和索引、手工发布补充记录、Milvus 手册片段。目录本身不是可以直接整体加载到前端的器件 JSON 库。

### 4.2 现有查询接口能做什么

| 文件 / 服务 | 可借鉴或复用 | 接入前需处理 |
| --- | --- | --- |
| `src/db.py` | 源/目标身份门禁、事务只读、绑定参数、连接关闭 | 为在线请求补连接与读写超时、查询预算；避免把整个 dataS 的发布能力引入工作台 |
| `query_service.search_device` | 型号规范化、发布视图、手工补充、来源链接 | 返回多条时直接取 `rows[0]`；主发布视图未直接支持标准 supplier 编号查询；手工补充只在主查询无结果时启用 |
| `priority_service.get_ordered_attributes` | 优先级、缺失标记、来源和手工属性 | 便利方法没有返回完整单位、定位、校验和等字段；工作台应查询完整字段或使用自己的只读适配器 |
| `core_service` | 核心器件画像与手册需求级别 | 画像是目录策略，不等于已核验、用户必须、已选用 |
| `full_chain_service.inspect_device` | 定位数据链断点，查看发布/来源/队列关联 | 多对象、多次计数和抽样，适合诊断；不是每轮对话的检索主路径，也不保证取到原始 PDF |
| `freshness_service.get_status` | 对比源/发布身份，输出可解释的新鲜度 | 全量身份扫描；应用做定时或缓存诊断；参数/引脚变化仍需其他校验和依据 |
| 手工补充的记录和工件表 | Published 原始输入、ATTRIBUTE_INDEX、SOURCE_LINK 等 | 使用独立命名空间；过滤发布状态；合并去重；保留补充记录自己的证据质量 |

本次一条用于对比手工记录与发布视图的相关子查询出现 `OperationalError`，改为两路只读获取后比较完成调查；没有修改数据库来绕过。在线实现应使用经验证的受限查询，不能把本轮探查 SQL 直接当成性能已验证的生产接口。

### 4.3 真实样本说明了哪些风险

**样本一：同名不等于唯一身份。** `LM358` 精确查询返回 3 条，制造商分别为 MSKSEMI、National Semiconductor、IDCHIP。`STM32F103` 前缀查询返回多个不同后缀型号。`search_device` 取第一条不适合作为用户器件确认逻辑。

**样本二：原值与单位字段可能不一致。** `TPS5450DDAR` / device 8883 / `C114425` 的源表 `switching_frequency` 为 `500kHz`；发布参数同时给出 `field_value_num=500`、`field_unit=Hz`，且 `evidence_status=PROVEN`。TI 官方产品页说明其开关频率为 500 kHz，也给出 5.5～36 V 输入范围。第三阶段应保留原值，在应用层验证转换和工况，给出冲突标记；不能把 `500 Hz` 当作可用的工程事实。[TI 官方产品资料](https://www.ti.com/product/TPS5450)

**样本三：缺失多，但不是用户要回答几万项。** 参数视图有 36,414 条 `is_missing=1`，其中 22,382 条同时 `is_required=1`。这是目录模板期望的资料字段，不能直接生成面向用户的问题。333,205 条非缺失记录没有单位，其中大量是名称、分类、封装等文本属性，这个数字也不能解释为“333,205 个数值参数有错”。

**样本四：身份更新会造成跨版本混用。** device 604 的发布名称是 `MMBT3904(RANGE:100-300)`，源库现在是 `MMBT3904`。两者不能只因为 ID 相同就被无条件拼成同一份最新证据；需要记录检查结果和所用快照。

**样本五：存在记录不等于工程上可用。** 示例器件价格为 null；数据库中有引脚或手册定位，只证明相应资料存在。额定值、适用工况、实际板级能力、库存和报价仍是独立问题。

## 5. Milvus 数据手册核查

现有工作台虚拟环境中已安装 `pymilvus 2.5.18`；本次连接到的服务器返回 `pkg/v2.6.13`。两个数据库都存在已加载的 `DataSheet` collection，本次标量查询和 BM25 检索均为只读，没有执行加载、建索引、写入或重建。

| 项目 | DataSheetBase | DataSheetBaseV2 |
| --- | --- | --- |
| TPS5450 / C114425 精确片段查询 | 返回片段 | 返回片段 |
| 片段定位 | id、section_path、chunk_idx 等 | 除左列外，还有独立 page_idx、source_run、ingested_at 等 |
| 本次英文参数词 BM25 查询 | 返回 3 条，但首条标题不能直接说明是目标参数 | 返回 0 条 |
| V2 中文/参数符号补测 | — | “输入电压”“开关频率”“VIN”“5.5V”分别返回 3 条 |

由此可以确认 V2 的相关样本存在，英文检索返回空不应被解释为“没有手册”。同时，相关性最高的片段也不一定包含可直接用于核对的参数，应进一步检查原文和工况。

其他需要落实的细节：

1. dataS 示例定位指向 `DataSheetBase`，现有知识工具默认指向 `DataSheetBaseV2`。两者应作为明确、可核查的数据源，不能静默互换后仍显示原来源。
2. 旧工具固定返回字段列表没有 `page_idx`、`source_run`、`ingested_at`，直接复用会丢失 V2 的定位信息。
3. 本次 V2 样本 `page_idx=0` 对应标题中的 PDF page 1。只有这个数据源的页码基准得到确认后才能显示“第 1 页”；不能用 `chunk_idx` 充当页码。
4. Milvus 主键大于 JavaScript 安全整数范围，跨 API 传递时应统一转成字符串，避免引用错片段。
5. 当前 schema 没有可直接认定为原始 PDF SHA-256、出版版本的独立字段。应用可以计算片段正文 hash，但不能称其为整份 PDF 的 hash。
6. 部分 `source_run` 元数据指向本次授权目录之外的路径。本次没有进入或读取这些路径。UI 可展示已取得的片段、页码和资料信息；原文件代理只能访问获准目录，不能沿数据库路径任意打开文件。

证据：[Milvus 只读核查 JSON](research/第三阶段_Milvus只读核查_20261016.json)。记录了 schema、索引名称、查询数量、片段 hash 和页码样本，未保存手册全文。

| [SQL 知识工具](../netlist_end_to_end/tools/sql.py) | 绑定参数、表名白名单、C/S 标识校验、限量与超时、原始参数和引脚读取 | 宽泛 LIKE 结果不能充当身份确认；原始两级分类不能替代 dataS taxonomy 或用户模块规范 |
| [Milvus 知识工具](../netlist_end_to_end/tools/milvus.py) | 精确 supplier 过滤、BM25、标量降级、有限条数 | 目前只在异常时降级，空命中另需处理；定位字段需扩展；不可跨型号补事实 |
| [器件资料预取](../netlist_end_to_end/tools/device_knowledge.py) | 确定性资料获取、批量、有限并发、状态说明 | 多个同类候选时挑一个代表 C 编号的策略不适合需求证据；片段截短不能充当完整参数证明 |
| [参考项目的 DeviceResolver](/share/home/chenxin/jlctest/01_PCBAgent/netlist_end_to_end/requirement_intent/agents/device_resolver.py) | 原文型号抽取、批量核验、禁止记忆补造、歧义保留 | 将 SQL 唯一和 Milvus 存在合成一个 confirmed，粒度太粗；“用户意图”和“工程满足”还需独立状态 |
| 参考项目 `requirement_intent/stage.py`、`catalog.py` | 匹配/缺失/歧义/错误状态、需求来源、报告组织 | 旧模块目录较粗；不得覆盖本项目的规范模块分类 |
| [generation_input.py](../netlist_end_to_end/generation_input.py) | 理解后续已选器件输入的边界、编写契约验证参考 | 它要求 already selected devices，不能直接消费尚待选型的需求说明书 |

推荐复制或抽取小范围的只读逻辑，形成工作台内部适配器；不通过修改 `sys.path` 导入 dataS 的通用 `src` 包，也不把完整旧 Agent 框架嵌入当前 Runner。需要复用的数据库连接参数通过部署配置提供，凭据不进入模型上下文、API 结果或导出文件。

## 7. 公开技术资料对方案的支持

以下资料于本轮核对，优先使用与现网相符的 MySQL 8.0、Milvus 2.6 文档。

| 官方资料 | 查证的能力 | 在本产品中的设计结论 |
| --- | --- | --- |
| [MySQL 事务访问模式](https://dev.mysql.com/doc/refman/8.0/en/set-transaction.html) | 支持事务只读；只读还有临时表等边界 | 使用固定读操作、身份检查和只读事务；不向模型开放 SQL 文本 |
| [MySQL 参数占位符](https://dev.mysql.com/doc/refman/8.0/en/sql-prepared-statements.html) | 参数占位可隔离值与 SQL 语法 | 查询模板固定，参数绑定；库表字段通过白名单处理 |
| [Milvus 2.6 过滤检索](https://milvus.io/docs/v2.6.x/filtered-search.md) | 检索可以施加元数据过滤 | 手册查询始终限定已解析的 supplier 标识和明确数据源 |
| [Milvus 2.6 全文检索](https://milvus.io/docs/v2.6.x/full-text-search.md) | BM25 支持原始文本查询，需要现有分析器、函数和索引 | 先使用现有 BM25，加中英文参数别名及精确查询降级；无需先建新向量库 |
| [FastAPI 同步与异步](https://fastapi.tiangolo.com/async/) | 普通工具函数直接从 async 调用时不会自动进入线程池 | 同步 SQL/Milvus 调用显式进入受限工作线程或作业，避免阻塞聊天事件循环 |
| [JSON Schema 对象约束](https://json-schema.org/understanding-json-schema/reference/object) | 对象字段限制会影响扩展兼容性 | 显式提升 schema 版本、提供迁移和旧版投影，不能往严格对象任意添加字段 |

这些资料支持的是底层能力。具体的器件意图、领域核对、交互优先级与交接政策是本项目基于本次数据观察提出的产品设计，需要后续开发和验收证明。

## 8. 调研结论

当前产品已经有可以扩展的对话、画布、规范模块、需求审核和恢复基础；资料库也有可用的真实器件、参数、来源和手册片段。第三阶段可以在现有架构内完成。

开发优先级应是：先建立身份、版本、单位和来源的可靠边界，再让这些事实进入对话、画布和影响分析，最后形成可交给选型方的 RequirementSpec。最需要防止的错误是：取同名第一条、把数据库 `PROVEN` 当工程通过、把目录缺失字段变成用户问卷、跨版本拼接证据，以及把“需求已审核”显示成“芯片和电路已验证”。

具体工作包、数据结构、UI 行为、接口和验收条件见[第三阶段领域能力补齐实施方案](需求分析工作台_第三阶段领域能力补齐实施方案.md)。
