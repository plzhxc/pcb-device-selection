# 第二阶段：深化持续需求收敛

日期：2026-10-15。目标是用户通过持续对话完成一份可审核、可追溯的需求说明书。基于第一阶段继续开发，保持独立服务、固定 Codex CLI / gpt-6-luna / xhigh，不接入器件检索、网表或原有自动模块分解流水线。

> 体验修订（2026-10-15）：V3目录属于参考，不要求用户确认全部247字段。默认展示产品决定，工程待办与完整规范分层；项目正文只列实际使用模块。审核依据是产品边界、实际需求、功能模块承接、流程和未决问题，不以全部技术模板闭合为条件。提交回答立即收起且服务端去重，过程可回看。最新实现与证据以[体验修复与真实使用记录](需求分析工作台_体验修复与真实使用记录.md)为准。以下保留第二阶段研究背景。

## 1. 回到最初目标

原始会话要求是：中心自然对话、右侧持续展示设计过程，用总结、问答、思维导图、框架和流程逐步形成完整说明书；先提供真实可用的 UI，再迭代领域能力。用户随后明确：未答不结束会话，分支可以积累，三问是每轮节奏，不能成为整个分析上限。

第一阶段已具备持久问题、补充队列、50 小节检查和审核。第二阶段解决更深的问题：一节写了总结并不证明该节字段齐全；用户不应为器件选型才能确定的细节无限回答；图中的模块必须出自指定规范，而不是六个需求分类方框。

产品面向普通产品负责人及硬件工程师：第一层只展示要做的决定、原因和影响；专业字段、端口角色、规范条目按需展开。用户已明确选择“两类都支持，分层呈现”和“给出建议与取舍，允许明确委托设计阶段”。用户再次强调：模块部分依模块规范，重点是类别而非编号；其他总体目标保持。

## 3. 参考项目的可复用点与不收敛原因

实际阅读 `jlctest/01_PCBAgent/netlist_end_to_end/requirement_intent/` 的 stage、catalog、anchors/modules/capability parser，以及 `web_console/services/runs.py::supplement`。

可复用的是稳定功能/模块实例编号、增量补充、value/status/source分离、功能→能力→模块关联、代码计算缺项、确定性 Markdown 和供电/数据/控制/时钟关系。继续采用同类数据模式与检查方法，不把整个 DAG 导入独立工作台。

| 观察 | 为什么不能靠重复调用收敛 | 第二阶段处理 |
| --- | --- | --- |
| DAG 的 repair/extend 主要修架构及覆盖 | 重试修结构，没有获得新的产品决定 | 区分内部复核与用户决定；状态持久，明确下一步 |
| missing_required 检查 required 和 tbd | 适用条件、阶段责任不充分时，后续实现参数一直是缺项 | 每个字段记录明确/不适用/委托设计/待确认/冲突及证据 |
| 模块仍为9子系统、19个宽类型 | 与10/60/197的粒度不同，命名对照无法代表已选类型 | 新规范目录单独登记，类型/实例/旧接口ID分开 |
| 模块提示要求 source_port、target_port、电压等，同时禁止无依据补写 | 需求文本没有引脚，模型应当保持tbd；再次运行不会产生证据 | 需求阶段记录角色及目标，真实脚号留待器件与原理图 |
| supplement 新建运行并传入旧报告 | 有补充能力，但运行完成和产品需求收敛仍是两回事 | 持久问题、字段账本、决策和文档版本属于产品层 |
| ground_report 包含数字/引文启发式及常用电源值例外 | 出现同一个数字不能证明其语义或适用条件 | 保留逐字来源；确定性计算只用结构化、同维度、同工况事实 |

另外只读抽样了 `output/requirement_codex_cli_15x/*/run-010/requirement_intent.json` 的27个结果：27份均为need_input，未决项每份1～7条，合计包括27条missing_required、10条device_ambiguous、63条model_note、2条capability_unprovided、1条function_uncovered。它们是同批次第10次独立运行的横截面，不是27次用户持续回答；有 open_items 不等于运行失败，也不能据此宣称全部15轮或冻结结果都失败。

例如机器人主控板的未决项包含部分功能缺少量化指标、系列名与明确料号的歧义，以及供电电压缺少依据。这些条目需要产品决定、来源或后续设计责任，重复运行同一原文不能自然补齐。不能为了冻结，把同一个数字或常用电压当成已核实证据。

## 4. 公开成熟技术及取舍

- 长程任务应有持久的细目、明确的完成条件和增量进展；不能只凭模型自己宣布完成。借鉴其工程方法，继续使用现有数据库及版本，不新引入一套 agent 框架。[Anthropic 长程 Harness 研究](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- 人机中断需要持久 checkpoint 和稳定 thread_id；等待不是丢掉任务，也不必持续消耗推理。借鉴其恢复和责任分界，保留现有队列/SSE，独立工作与待回答任务分开。[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- 交互应说明系统能力与不确定性，允许纠正、控制和反馈。落地为带依据的建议、明确的未决项、修改影响及用户审核。[Microsoft 人机交互指南](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)
- Claude 的问题通过应用展示与回传，等待可以持续保留；应用需区分澄清问题和普通对话轮次。借鉴问题与答案的明确关联，不搬入其权限审批机制。[Claude 用户输入](https://code.claude.com/docs/en/agent-sdk/user-input)
- OpenCode 的 question 支持选项与自定义答案。继续采用普通文字选项，并加上决策影响、取舍与自由输入，不让用户记忆内部编号。[OpenCode Tools](https://docs.opencode.ai/docs/tools/)

现有 React/SVG 已能呈现需要的图，不为流程图引入完整可视化编辑器；规范树和模块卡用原生组件。数值一致性检查与进度来自服务端确定性代码，LLM 负责提取、解释、提出候选和必要问题。继续使用 CLI，未来 App Server/Harness 只作为运行层适配选项。

## 5. 用户旅程与画布

1. 用户描述产品：AI 总结“已理解什么”，记录功能与边界。
2. 优先提产品用途、关键指标、供电/约束和验收问题。每次少量，说明为何要问以及各选项的取舍。
3. 右侧收敛视图展示产品目标→功能与约束→规范模块→接口/一致性→最终审阅。只读进度可展开定位到具体字段，不向用户抛出247项问卷。
4. 模块方案提供10类/60父/197子目录的搜索、筛选、规范卡和实例列表；实例关联需求与数量，显示类型层级、边界、来源、抽象端口。用户可直接添加、调整或移除，并进入版本记录。
5. 多分支回答后，按稳定决策范围合并和排序；已由证据闭合的字段不再反复问。不知道时提供合理候选，只有明确授权才登记设计阶段责任。
6. 跨需求修改会使关联字段、模块关系或数值事实重新核对；画布显示影响，不能沿用旧审核。
7. 核心及已有依据的产品决定、必要功能模块覆盖、确定性冲突、待答问题均处理完，才进入用户审阅；未知实现参数保持待设计，不要求为填写模板反复授权。设计阶段交接是有边界、有依据的任务，不是把缺项隐藏。

界面保持中心对话及右侧画布。在总览补充简洁收敛概况，另设“收敛路径”和“模块方案”专业视图；正文与图形引用同一版本。移动端标签横向滚动，详情按需展开，卡片无全页横向溢出。

## 6. 后端方案

- **规范目录层**：只读版本化目录，字段使用稳定ID；模块类型编号通过枚举/服务校验，不接受自由新建规范类型。
- **事实与决定层**：247字段账本按字段或有共同证据的字段组更新；状态、结论、需求引用与逐字来源分开。章节总结不能直接代替字段完整性。
- **模块层**：项目实例稳定ID、规范type_id、数量、用途、边界、需求引用、确认状态及来源；关联边记录供电/数据/控制/时钟及抽象端口，不虚构器件脚号。
- **一致性层**：同一量、对象、工况的数值范围交集检查；单位规范化；电池容量/平均电流/续航的理想上界等有限规则。缺少输入就显示待核实，不估算成通过，不把成本/性能偏好机械判为不可能。
- **对话调度层**：问题关联字段和决策范围，优先冲突与前置决定；回答只解决有证据的分支。无进展可见，明确说明卡点，保留用户控制。
- **提交层**：沿用单项目串行、基线版本、原子保存、幂等与补充队列；手工编辑和AI更新共享失效规则。
- **终稿层**：旧版结果标明使用章节核对，下一轮分析升级字段核对；新协议的审核条件由代码计算，模型不能通过只输出50个confirmed跳过细目。

## 7. 开发与迭代验收

先提取并核对目录，再实现服务端模型和检查，再接入收敛/模块画布与问题卡，最后进行真实 Codex 和受控随机压力测试。开发中发现不可行处，记录“假设→试验→修正→证据”，方案随实现更新。

两轮随机case使用不同随机种子，覆盖不同产品功能与模块、部分/延迟回答、反复修改、模块选择、规范越界、数值冲突、刷新、停止和并发补充。受控替身用于可重复故障与负载，真实CLI用于语义与多轮收敛；两类证据明确区分。交付一键构建/启动/测试脚本和最终操作说明，受控故障不写入正式用户项目。本次用户明确要求可在正式UI查看完整过程，因此另建标明“体验实测”的独立真实会话，保留用户可看的正常记录。

## 8. 实测驱动的修正

1. 起初只提取父类名称，不足以帮助选择类别。随后补全60个父类的功能契约、组合排除、抽象接口、组成和复核规则；197张子类卡及参数表继续完整保留。
2. 实测发现把模块名称或用途的措辞变化当成结构变化，会反复打开已知字段。现按类别、数量、功能关联及纳入/排除变化触发模块影响复核；描述性改写不清空事实。
3. 真实案例的设计寿命“3年”曾被数值检查误报为未知单位。现允许年/月在相同日历单位内比较，不擅自折算为固定秒数。涉及电量计算时仍要求明确的时长口径。
4. 模型曾用两个null边界返回数值条目，结构字段存在但业务不成立。现提供明确校验反馈，单轮最多自动修复一次；修复与首轮共享原超时预算，失败保留原版本，停止也覆盖修复中的子进程。越界工具和调用失败不自动重试。
5. 字段账本把共同结论与长引文重复存储，直接传入模型会放大上下文。现仅在模型输入中无损分组；持久化、来源与UI完整保留。实测一份真实文档由约132KB降为64KB；压缩比例取决于重复程度，不作为固定性能承诺。
6. 已有逐字依据的“无交付日期约束”不应为了闭合字段再复制一条REQ。现允许非核心字段直接由用户依据支持，核心产品目标与功能继续要求关联需求；无关联的已明确字段在后续需求变化时保守复核。

实现和最终证据见[第二阶段开发与验收](需求分析工作台_第二阶段开发与验收.md)。
