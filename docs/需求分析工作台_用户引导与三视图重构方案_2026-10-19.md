# 需求分析工作台：用户引导与三视图重构方案

日期：2026-10-19。范围：在现有工作台上进行小范围重构，改善 AI 指引、规范说明书、收敛路径和模块方案。只做两个真实模型的开发使用案例，最终验收由用户完成。本文先记录设计依据，开发结果和调整另在末尾追加。

## 1. 产品重新对齐

用户希望从一句不完整的产品想法出发，由 AI 帮助判断、给出建议、解释取舍，再作出少量必要选择，最终得到符合《硬件需求说明书章节规范 V3.0》的本项目说明书。客户不应预先知道电路拓扑、器件型号、接口电平或所有验收数值。

工作台需要让用户随时看懂四件事：我已经说了什么；AI 从中整理出了什么、建议了什么；现在需要我决定什么；这个决定怎样改变说明书和模块方案。规范用于组织产物与检查遗漏，不能成为要求普通客户逐项填写的问卷。

右侧只保留三个入口：**需求说明书、收敛路径、模块方案**。设计总览和变更记录不再作为独立视图。原对话、版本、图形操作、器件证据与交接能力继续保留，版本变化归入收敛路径。

## 2. 已核实的问题与原因

### 2.1 规范与正文不一致

当前正文使用“产品目标与场景、功能与使用体验”等简化标题，没有按 V3 的章节、条款逐条对应展示。完整字段目录在另一个专业视图，用户无法直接核对说明书是否覆盖自己关心的项目。应恢复 V3 的章、节和条目名称，明确每条当前内容及状态。

### 2.2 收敛路径显示的是清单进度，缺少决定的来龙去脉

当前页面以阶段、数量、字段筛选为主，缺少“输入—分析—选项—选择—结果”的因果关系。历史版本的待定结论容易被误读为当前仍未解决；已提交答案、真正得到明确结论、AI 建议和后台关联复核也没有形成一条易读的路径。

### 2.3 内容存在多份表达，更新可能遗漏

现有结构分别保存需求条目、字段结论、模块边界和问题历史。关联需求修改时，字段会被置为待复核；模型需要分别更新多处表述。历史 FOC 第二轮案例 v14 中，用户已经选择约 30 W、且只要求编码器/霍尔接口，REQ-004/014/015 仍残留“未给出”“未说明”。问题关闭和字段确认不能证明整份文档语义已经同步。

处理原则：显示始终引用当前需求对象；对新决定影响的关联条目设置内部复核任务；模型必须实际修改或明确复核这些条目，不能只在回复中说“已更新”。代码能够验证引用、版本和复核动作，不能替代硬件语义判断，因此仍保留最终人工审阅。

### 2.4 AI 与用户的分工不够清楚

过往验收输入包含大量专业条件，不能代表真实新手。产品范围、使用方式、关键效果和验收取舍应由用户决定；从已有信息能整理的字段、模块分类、实现待办应由 AI 完成。没有明确指标时先给少量容易理解的建议，不能要求客户自己发明参数；用户说“不知道”也不等于接受推荐方案。

## 3. 调研与本项目采用的做法

资料核对日期：2026-10-19。以下是产品设计参考，并非引入新框架的承诺。

| 官方资料 | 可借鉴的原则 | 在本项目中的用法 |
| --- | --- | --- |
| [GOV.UK Question pages](https://design-system.service.gov.uk/patterns/question-pages/) | 明确每个问题为什么必要，允许合理的“不知道”，避免重复收集已有信息 | 默认每轮一个主要决定；必要时两个密切相关问题。保留自由输入与其他未答分支 |
| [GOV.UK Check answers](https://design-system.service.gov.uk/patterns/check-answers/) | 按相关章节核对答案，允许修改，修改影响后续内容时补问 | 说明书按规范条款核对，决定可以回到对话修改；仅重开受影响的分支 |
| [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) | 人工输入要持久保存，并与相应任务关联后恢复执行 | 沿用现有问题 ID、回答回执、补充队列和版本提交，不迁移整个运行框架 |
| [W3C PROV Primer](https://www.w3.org/TR/prov-primer/) | 区分来源、处理活动、结果和修订关系 | 收敛路径连接用户消息、AI 整理、真实回答和当前需求；历史结果标明后续调整 |

这几项参考推导出的产品方案是：少量必要问题、清楚的来源与状态、可修改的决定、同一份数据的多种呈现。继续使用 React/FastAPI、现有图形组件和 Codex CLI，不新增重型流程引擎。

## 4. 一次合理的需求分析怎样进行

### 4.1 从模糊想法到产品边界

1. 用户输入一句想法，例如“想做个放在书桌上的温度显示器”。
2. AI 立即整理已有事实：桌面使用、测量温度、本地显示；产品工作名称可以暂拟，不能因此阻塞流程。
3. AI 先问影响方案的主要选择，例如是否需要离开电源使用，并给出可理解的取舍。不要同时询问 ADC 位数、板层、滤波、晶振和所有认证。
4. 用户只回答一个问题也能推进。提交后选项收起，回执明确“已收到，正在整理”，不能继续重复选择。
5. AI 将实际回答写回当前需求及关联字段，整理模块责任，给出下一项真正必要的选择。

### 4.2 区分事实、建议、授权和未知

- **用户已明确**：用户直接提出或真实选择的内容；保留原消息依据。
- **AI 建议，待选择**：存在方案与理由，但用户尚未同意，不能冒充已确认。
- **用户明确委托设计**：记录委托范围和必须满足的产品目标，不宣称工程验证完成。
- **待用户决定**：缺少会改变用途、功能、安全行为或验收方式的取舍。
- **AI 关联复核中**：答案已经收到，需要统一旧内容，不要求用户再回答同一问题。
- **未提出要求 / 待设计评估**：规范中存在该项，但本项目还没有相应硬指标；不自动标为不适用，也不自动作为阻塞问题。
- **明确不纳入本版**：用户确实排除的范围，保留边界说明。

### 4.3 什么时候结束提问

结束条件是产品核心目标、实际要求和关键体验可理解且可检查，必要硬件功能有模块承接，真实冲突及未答问题已经处理，关联内容已复核，用户可以审阅完整产物。不是固定三问，也不是填满 247 个字段。具体芯片、引脚、PCB 工艺和没有额外要求的工程细节可以保留待设计任务。

用户修改决定时保留旧选择及变更依据。新的选择替代旧内容，受影响的模块和要求进入内部复核，只有出现新的实际产品取舍才再问用户。

## 5. 需求说明书视图

### 5.1 结构

按 V3 顺序呈现：元数据表；第 1 章项目概述；第 2 章功能需求详解；第 3 章性能指标；第 4 章生产与测试；第 5 章电路模块分析。条款逐项显示“名称、当前要求、状态、依据/关联需求”。功能名称、描述、指标、输入输出要能追溯到实际功能条目。

第 5 章的模块类别以较新的模块规范为准，使用 10 大类、60 父类、197 子类中的实际项目类别，不照抄 V3 旧九类的完整模板。显示本项目系统框图、实际模块、功能责任及模块间抽象关系；不把未使用类别写入项目说明书。

第 6 章依规范属于审核后的选型，当前阶段只说明已提及器件的使用意图、已取得资料和待选型边界，不能自动编造候选结论或完整 BOM。来源、参考资料、实际修改记录作为附录保留。

### 5.2 阅读方式

默认按章节阅读；项目概述和实际功能优先展开。专业参数按小节折叠，展开后仍逐条可见，不用横向挤压的大表格。支持按条款或内容搜索、查看依据、回到对话讨论。规范完整性与需用户回答的问题数量分别显示，不能把参考字段覆盖率当成客户完成率。

当前已明确内容直接引用本版需求；旧字段结论只在历史依据中保留，不能在当前要求旁继续显示为待定。用户已答但内部尚未整理完成时明确提示这一状态。

Markdown 导出也按同样的规范结构、当前要求和状态生成，与页面共享同一个条款投影，避免页面正确而下载文件仍是旧结构。系统框图和流程图沿用可缩放、平移、拖动的画布。

## 6. 收敛路径视图

以可读的纵向树展示，而非横向铺开的大型节点网：

```text
用户的想法 / 补充
  ├─ AI 整理：已有事实与本轮建议
  ├─ 需要选择的事项
  │    ├─ 方案 A：取舍说明
  │    ├─ 方案 B：取舍说明
  │    └─ 用户实际回答 → 当前结果 → 影响的条款 / 模块
  └─ 后续分支：待回答 / 已收到 / 内部复核 / 已完成 / 后来调整
```

路径展示公开的分析摘要、建议和证据，不展示模型私有推理。每个决定可定位实际原话、查看当前相关需求、跳转模块方案或继续修改。

默认突出当前需要操作的分支和最近进展。历史选择折叠保留；如果后来改了供电或范围，旧分支明确显示“后续已调整”，当前值以最新对象为准。不能用历史快照的状态重新覆盖当前决定。

对于老会话：从已保存版本、原话、问题历史和真实回答还原已有路径，并标注“历史版本整理”。缺失的推荐理由或选项不编造。新会话在提交版本时保存来源消息和公开回复的关联，便于准确追溯。

## 7. 模块方案视图

先回答“这个产品需要哪些功能电路”，再提供规范目录供专业用户展开。每张卡按人类阅读顺序展示：

1. 在产品中的作用；承接的具体功能与要求。
2. 选用的规范大类、父类或子类；无需客户识记编号。
3. 当前是 AI 提案、用户已确认类别用途，还是用户委托设计。
4. 已确定的产品边界与待设计内容；不混为已经验证的电路。
5. 与其他模块的供电、数据或控制关系；可查看器件证据。

模块方案只展示实际纳入和当前建议项；已排除项折叠在范围历史。完整类别库默认收起。未知实现可停留在职责适合的父类，不强行指定芯片。一项功能可以由多个模块承接，一个模块可以承接相关多项功能；独立电路数量不能等同于芯片数量。

类别和职责已有用户依据后沿用，不为每个内部实现细节再次索要批准。确实需要用户作出的架构取舍用通俗语言在对话中提出，方案审核保留可查看完整清单的显式操作。

## 8. 后端与数据设计

### 8.1 同一份对象，三个视图

需求条目及其来源继续作为实际要求的基本对象；规范字段保存关联和核对状态；模块引用这些需求。新增条款归属使模型能把每项要求准确挂到 V3 字段，旧数据兼容原字段关联。页面与 Markdown 都由服务端同一份条款视图产生。

收敛路径引用对象 ID 及当前值，版本只负责解释变化。新版本保存“来自哪条输入、属于哪次分析、公开回复是什么、实际回答了什么”的关联，不另让模型生成一份独立的决策历史。

### 8.2 关联复核

处理已回答问题时，收集问题关联需求、字段原有需求与本轮新关联需求。未实际更新的相关条目进入内部复核；模型可修改内容，或明确返回已检查且仍有效的条目 ID。复核待办参与审核条件，由内部续分析处理，不能变成要求客户再次补充同一事实的问题。

来源验证、用户确认与 AI 建议分离继续保留。没有真实用户原话不能把提案提升为确认。删除、改型、数量与指定器件约束继续受原校验约束。内部复核动作本身不等于语义正确或器件可用，最终由模型分析与用户审阅共同判断。

### 8.3 兼容与范围

不更换 Codex CLI 集成，不引入新的完整 Agent 运行框架，不迁移到原生长期 CLI 会话。保留当前独立工作台、持久输入队列、版本冲突保护、来源锚点、真实数据库只读查询、证据与后续适配。历史版本不改写成新的“成功记录”，旧测试缺陷保持可查。

## 9. 开发顺序

1. 保存源码基线，隔离运行开发服务，保留主工作台原项目。
2. 建立规范条款投影、实际路径数据和关联复核；补充有针对性的逻辑检查。
3. 调整 AI 引导：短输入能推进，默认单个主要决定，既有决定复用，内部整理不推给客户。
4. 替换右侧三个视图，删除两个独立入口，整理模块卡与专业目录层级。
5. 构建前端，并通过两个实际用户案例观察、调整与记录。
6. 备份主数据，在无活动任务时更新服务，保留这两个开发过程供用户在页面查看。

## 10. 两个开发使用案例

案例一从“想做个书桌上看的温度显示器，不懂硬件”开始；只按 AI 实际提问逐次回答。观察是否先问有用问题、是否避免专业问卷、说明书是否逐条归位、回答是否收起、确认内容是否同步。

案例二从另一个简单产品想法开始，例如“想做个提醒我喝水的小东西”。在 AI 引导后修改一项已决定的使用方式或提醒方式，检查旧选择如何保留、新结果如何更新、相关模块与条款如何复核。不给预先编好的完整技术条件。

测试记录包括原始输入、AI 实际回复、每次回答、条款/模块变化、发现的问题和修复结果。开发途中只使用这两个产品，不扩展旧的大规模案例矩阵。两个案例可以在同一项目中继续纠正开发问题，但不伪称一次成功或最终验收通过。

## 11. 本轮交付与边界

交付为可查看使用的更新工作台、本文方案、实际开发记录和两个留在 UI 中的使用过程。用户最终判断交互与说明书质量。本轮重点是让决定、状态、规范结构和模块职责可理解、可追溯、可修改；不承诺自动完成完整原理图验证或穷举所有产品的语义正确性。

## 12. 开发结果

本轮已完成三视图与 AI 引导的实际开发，保留既有模型、队列、证据和交接边界。规范逐条投影与导出共用数据，真实决定的依赖复核已参与审阅条件；路径以保存版本及真实来源生成，未另建需要模型维护的独立决策文本。

实际使用中补充了状态变化通知、方案页直接采用、长确认范围折叠、正文定位、分视图阅读位置，以及小规模框图随宽度调整。最后按字段摘要收拢重复的大段功能描述，并使设计目标关联已知核心性能；完整要求仍保留在功能描述中，复核中不使用旧摘要。这些是根据两个真实过程和截图发现的问题作出的细化。

两个案例分别为书桌温度显示器 v18（9 次输入）和工位喝水提醒器 v16（10 次输入），均处于待审核状态，等待用户最终确认。一次外部模型连接失败通过 UI 重试恢复，保留了真实记录。详细输入、选择、修正、开发检查与链接见[开发记录](需求分析工作台_三视图重构开发记录_2026-10-19.md)。

已在主工作台保留两个过程，原有 113 个项目及各表旧记录通过逐行摘要检查，新增后共 115 个项目。
