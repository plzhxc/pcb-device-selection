## 1. 产品目标

构建以持续对话驱动的硬件需求分析工作台：左侧管理项目，中间与 AI 交流，右侧持续呈现一份图文结合、逐轮完善的需求说明书。用户可以从模糊想法开始，通过总结、提问、补充、修改和确认，形成可阅读、可追溯、可导出的需求文档。

最终业务交付包括需求说明书、结构化 RequirementSpec、问答与修改记录。工作台独立开发和运行；第三、四阶段通过明确契约输出后续选型项，并适配现有流程输入入口。验收范围为需求及输入可读，不要求在此完整运行网表流程。

## 2. 已核对的项目事实

- 当前 work/01_PCBAgent 的现有 Web Console 使用 React、TypeScript、Vite；服务端使用 FastAPI。现有生产入口并不构成这里需要的持续需求分析产品。
- `../../../jlctest/01_PCBAgent/netlist_end_to_end/requirement_intent/` 包含真实需求解析：产品与约束提取、器件识别、模块分析、能力对齐、缺项检查和报告生成。
- `anchors_parser.py` 值得借鉴稳定功能编号、值/状态/来源及补充模式。
- `catalog.py` 值得借鉴字段目录、缺项与来源检查、由结构化数据确定性渲染 Markdown。现有来源检查包含启发式，不能视作完整的语义证据证明。
- `web_console/services/runs.py` 中 `supplement()` 已支持基于旧报告补充，但它创建新的测试运行；持续会话、文档版本和画布同步仍需新的业务实现。
- `tools/codex_requirement_runner.py` 已使用真实 Codex CLI：`codex exec --ephemeral --ignore-user-config --sandbox read-only --skip-git-repo-check --json -m gpt-6-luna -c model_reasoning_effort="xhigh" --output-schema ...`。其原用途是离线批量流程，整体搬入在线工作台会带入无关阶段。
- 最新《需求分析与器件选型功能设计及分工》取消独立自动模块分解；RequirementSpec 与 CandidateSet 通过需求版本关联，资料核验与用户选用是不同状态。

## 3. 界面与交互方向

桌面三栏：项目侧栏约 220px，对话区约 500px，右侧使用剩余空间。支持收起侧栏、调整对话/画布宽度、窄屏切换。采用中性色、细分隔线、清晰正文与少量强调色。

对话显示用户输入、AI 总结、本轮修改说明及问题卡片。每轮优先提出少量影响最大的关键问题，提供选项和自由输入，允许“不确定”。

本次用户进一步明确：少量问题只是每轮交互方式，最终必须多轮收敛整份说明书。当前已将问题持久待办、分支累积、分析中补充队列、50 个 V3 小节核对及用户终稿审核纳入实现；不以“三问答完”或模型暂不提问为完成条件。详见[最新验收](需求分析工作台_压力测试与收敛验收.md)。

画布当前提供“需求说明书 / 收敛路径 / 模块方案”三个视图。说明书按 V3 章节及条款逐项阅读，保留本项目系统框图和工作流程；收敛路径按用途、功能验收、供电接口、器件条件、模块承接五个主题显示当前决定、依据、实际关联和待决分支，聊天仅保留在对话区，原话与历史值按需展开；模块方案说明实际功能的承接职责、规范类别、用户决定与待设计边界。原总览与独立变更页的导航已移除，历史数据继续用于追溯。

更新应由真实业务事件驱动。保存新版本后高亮变化，保留用户阅读位置。显示已采纳需求、建议、修改原因、来源和待确认事项。

## 4. V3.0 规范的使用方式

[硬件需求说明书 V3.0](../硬件需求说明书章节规范（带+Agent+Prompt）+V3.0.md)作为完整字段目录、章节骨架和修改规则参考。交互按项目适用性逐步展开：

1. 优先明确产品用途、场景、核心功能、优先级、供电、关键指标和成本边界。
2. 根据需求触发条件字段：电池→续航，传感→精度，户外→环境与防护，无线→距离等。
3. 制造细节、特定认证和复杂测试条件按需要细化。
4. 固定功能分类用于组织框架，不额外启动自动模块分解流程。
5. 记录用户对器件的指定/偏好/参考意图；第三阶段补齐真实只读资料、身份歧义与必要条件核对，最终候选定型和完整BOM仍属于后续选型。

草稿允许未知项。来源（用户原话、AI 建议、数据库资料）与确认状态分别记录。“待定”与“不适用”需要区分。进入后续流程前再处理会阻塞该流程的缺项和冲突。

## 5. 单一需求依据

对话 → 提取修改 → 来源/结构/冲突校验 → 保存需求版本 → 同步正文、表格、图形 → 下一轮问题。

核心对象：项目、消息、需求条目、问题、决策、版本和图形关系。需求条目具备稳定编号、分类、名称、值、单位、优先级、状态及来源。模型提出修改，业务服务负责校验与提交。

直接编辑与 AI 修改共用版本规则；生成中断保持上次已提交文档；并发编辑通过基线版本检查避免覆盖。

## 6. 问答机制参考

- Codex App Server 的结构化用户问题请求支持短问题、选项及回答/中断生命周期。
- Claude Agent SDK 的 AskUserQuestion 通过应用展示选项并返回回答。
- OpenCode question 支持选项与自由输入，并有取消行为。

领域策略：先呈现已理解内容，再问 1～3 个关键问题；说明选项影响；记住已回答问题；对需求变更解释关联影响；不将默认经验数值写成用户已确认事实。

## 7. DeepSeek Harness 调研

官方仓库确实存在，采用 MIT 许可，当前标记开发者预览并说明将有破坏兼容性的变更。模型 API 接入与 Harness 接入是不同决策。

已公开的相关能力：插件式智能体运行、右侧面板/React 扩展、结构化问题、会话与事件、Python SDK。右侧面板可承载需求画布，但内部 dockkit 不是稳定扩展接口。Python SDK 通过子进程 JSON-RPC 运行；Web 应用是独立入口，不能假设 SDK 自动完成网页提问回传。

| 路线 | 收益 | 成本 | 当前判断 |
| --- | --- | --- | --- |
| 自有 React + 现有 Python 框架 | 与现有代码贴合、业务控制明确 | 需补齐持续会话与版本 | 长期基线候选 |
| 自有 React + Harness 运行层 | 借用会话/工具机制 | SDK、事件、问答适配 | 可做独立验证 |
| Harness Web + 画布插件 | 借用工作台宿主 | 插件学习及 Python 服务桥接 | 可选宿主 |
| 整体迁移 | 统一运行体系 | 范围大、兼容变化成本 | 首阶段不采用 |

实际接入前验证：流式事件、提问回答取消、刷新恢复、领域工具桥接、业务修改校验、项目隔离和固定版本部署。官方 sdk-minimal 文档还说明 shell 权限及会话日志默认行为，产品接入需单独配置工具与日志策略。

当前用户确定：第一阶段固定接入 Codex CLI，界面显示 gpt6-luna-xhigh，实际命令使用参考项目的 gpt-6-luna + xhigh，不引入 Harness。

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 1 UI 与基础使用 | 独立工作台、真实 Codex 基础问答、图文联动、保存编辑导出、文档 | 可实际查看和操作，样式与核心操作通过评审 |

| 4 需求分析验收 | 固定案例与真实模型评估，下游契约验证 | 图文一致，关键缺项处理，输出可被后续消费 |
