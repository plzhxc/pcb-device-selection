# 器件选型阶段设计

- 负责人：郑智齐
- 版本：v1（2026-10-16）
- 依据：《需求分析与器件选型功能设计及分工.md》《会议要求.txt》《数据库信息.txt》
- 代码：`device_selection/src`、`device_selection/web`

---

## 1. 阶段定位

**输入** `RequirementSpec`（需求分析确认后的选型项清单）
**输出** `CandidateSet`（按选型项组织的候选清单 + 用户决定）
**下游** 转换为 `pcbagent.netlist_input.v1`，喂给 `netlist → top_port`

阶段只回答一个问题：**这些需求，目录里有哪些真实器件能承担，依据是什么。**
它不生成需求，不决定架构，也不替用户拍板。

### 1.1 与会议要求对齐

| 会议要求 | 本设计的落实 |
| --- | --- |
| 器件选型清单用列表形式，不做复杂页面 | 主视图就是一张表，一行一个候选 |
| 重点展示：模块、芯片型号、参数、优势劣势、成本 | 表格七列：型号 / 关键参数 / 优势 / 劣势与风险 / 成本 / 结论 / 你的决定 |
| AI 对话框 + 画布渲染 | 左侧对话面板，右侧清单；对话改条件后清单真实重算 |
| 渐进式展示 | 每行默认只给结论与关键参数，展开才看逐条证据；淘汰候选折叠 |
| 接陈鑫整理的 SQL 快照 | 已接 `device_parameters_dev`，账号与地址按《数据库信息.txt》 |
| RAG 先定位器件类型再查参数 | 召回先走 taxonomy 的 `leaf_code`，再读该器件的属性优先级表 |
| 固定 case 测试 | `specs/` 放固定需求清单，每次改动都复跑同一份 |

## 2. 数据基线（2026-10-16 实测）

目标库 `device_parameters_dev`，MySQL 8.0.42，本机 socket 连接验证通过。

| 项 | 实测值 |
| --- | --- |
| 器件数（`dsearch_v_device_search_profiled_incremental`） | 9010 |
| 属性行数（`dsearch_v_device_attribute_priority_incremental`） | 377194 |
| 表 / 视图 | 88 张表、16 个视图 |
| 证据状态分布 | PROVEN 340779、EXPECTED_BUT_MISSING 36157、PARTIAL 258 |
| 带数值的属性 | 130871 行 |
| 其中**没有单位**的 | 127863 行（98%） |
| 价格 / 库存字段 | **整库不存在** |

### 2.1 两个必须先说清的坑

**坑一：数值字段不可直接信。** 以 TPS5450DDAR 为例，开关频率的
`field_value_text` 是 `500kHz`，但 `field_value_num = 500`、`field_unit = Hz`。
直接拿数值列比较会把 500 kHz 当成 500 Hz，差 1000 倍。本实现的规则是
**以文本为准**：能解析带单位的文本就用文本，只有文本不可解析时才退回数值列，
且没有单位时标记为不可信。

**坑二：这个库不提供成本。** 全库没有任何价格或库存列。成本只能来自预设元件库
（`legacy/device_selection/assets/preset_components.json` 的 `price_cny`）。
查不到就标「待确认」，不计入合计——按红线不能按 0 元算。当前示例的三个选型项
全部落在「待确认」，这正是真实状态，不是缺陷。

### 2.2 用到的视图

| 视图 | 用途 | 关键列 |
| --- | --- | --- |
| `dsearch_v_device_search_profiled_incremental` | 器件身份与类别 | `device_id`、`part_number_normalized`、`leaf_code`、`legacy_level2`、`component_role`、`phase2_core_level`、`milvus_source_locator` |
| `dsearch_v_device_attribute_priority_incremental` | 参数与优先级 | `field_key`、`field_value_text`、`field_value_num`、`field_unit`、`priority_rank`、`is_required`、`is_missing`、`evidence_status`、`source_locator` |

`priority_rank` 小于 9999 的是该类别的关键参数；`is_required` 标出必填；
`evidence_status = EXPECTED_BUT_MISSING` 就是「应该有但没采到」，直接对应
「待补证据」。

## 3. 阶段流程

```
RequirementSpec
   │
   ├─ 1. 生成选型条件：类别 / 数量 / 硬性条件 / 偏好条件（每条挂需求编号）
   │
   ├─ 2. 候选召回：指定型号 → 精确查；未指定 → leaf_code → legacy 二级类别 → 关键词
   │
   ├─ 3. 参数归一化：文本优先解析，单位换算到基准单位
   │
   ├─ 4. 三态判定：满足 / 不满足 / 未知 —— 违反硬性条件直接淘汰
   │
   └─ 5. 组装清单：排序、去重、价格标注、阻塞说明
   │
CandidateSet（+ 用户决定：保留 / 排除 / 待讨论 / 已确认）
```

任何一步召回为空都如实返回空列表，绝不用模型记忆补造型号。

## 4. 数据契约

### 4.1 输入 `RequirementSpec`

```json
{
  "schema": "pcbagent.requirement_spec.v1",
  "requirement_version": "req-demo-0001",
  "project": {"name": "…", "summary": "…"},
  "global_constraints": {"budget_total_cny": 120, "currency": "CNY"},
  "selection_items": [
    {
      "id": "SEL-001",
      "category": "dc_dc_power_converter_chip",
      "leaf_code": "l_step_down_dc_dc_converter",
      "quantity": 2,
      "related_requirements": ["F01"],
      "hard_conditions": [
        {"field": "topology", "op": "contains", "value": "Buck",
         "reason": "必须是降压拓扑", "related_requirement": "F01"}
      ],
      "preferred_conditions": [
        {"field": "output_current", "op": ">=", "value": 5, "unit": "A"}
      ],
      "specified_device": {"model": "TPS5450DDAR", "intent": "preferred"}
    }

```

支持的条件比较符：`>=`、`<=`、`>`、`<`、`==`、`!=`、`cover`（能力区间覆盖需求区间）、
`is`、`is_not`、`in`、`not_in`、`contains`、`not_contains`。

`specified_device.intent` 取 `must` / `preferred` / `reference`，分别对应需求侧的
「必须使用 / 优先考虑 / 仅作参考」。

## 5. 判定规则

`fit` 的取值由证据决定，不由模型偏好决定：

| fit | 含义 | 触发条件 |
| --- | --- | --- |
| `recommended` | 推荐 | 硬性与偏好条件全部满足，无未知项 |
| `acceptable` | 可接受 | 硬性条件满足，存在未知项但不影响结论 |
| `conditional` | 有条件 | 有硬性条件处于未知（证据待补），不能当满足 |
| `excluded` | 已淘汰 | 任一硬性条件明确违反，不进推荐列表 |

`confidence` = 满足条数 / 判定的总条数，只反映证据完整度，不是主观打分。

### 5.1 单位归一化

以文本优先，解析带 SI 前缀的数值并换算到基准单位（V / A / Hz / F / H / Ω / W / °C / s）。
条件里的单位同样换算，两边单位不一致或未知时判为**未知**，而不是猜。

实测效果（`specs/example_power.json` 的 SEL-001）：

| 条件 | 器件原文 | 归一化后 | 判定 |
| --- | --- | --- | --- |
| `switching_frequency >= 400 kHz` | 500kHz | 器件 500000 Hz vs 条件 400000 Hz | 满足 |
| `output_current >= 5 A` | 5A | 5 A vs 5 A | 满足 |
| `input_voltage_range cover 4.75~5.25V` | 该字段缺失 | — | 未知 → `conditional` |

## 6. 网页端界面

### 6.1 布局

```
┌──────────────────────────────────────────────────────────────┐
│ 项目名 / 需求版本            选型项 3 · 有推荐 3 · 阻塞 0 · 成本待确认 3 │
├────────────────┬─────────────────────────────────────────────┤
│ 选型助手        │ SEL-001  dc_dc_power_converter_chip · 数量 2 │
│ （对话）        │ ┌──────┬──────┬──────┬──────┬────┬────┬───┐ │
│                │ │型号  │参数  │优势  │劣势  │成本│结论│决定│ │
│  总结一下清单   │ │TPS5450│…    │满足… │—     │待确│推荐│按钮│ │
│  为什么选 X     │ └──────┴──────┴──────┴──────┴────┴────┴───┘ │
│                │  ▸ 展开证据（3 条判定 · 数据源 …）            │
│ [输入框] [发送] │ Sel-002 …                                    │
└────────────────┴─────────────────────────────────────────────┘
```

### 6.2 交互

| 交互 | 行为 |
| --- | --- |
| 展开证据 | 每条条件列出 满足 / 不满足 / 未知，附说明、来源需求编号、`device_id` 与手册 locator |
| 保留 / 排除 / 待讨论 / 确认 | 记录用户决定，与资料核验状态分开保存 |
| 对话提问 | 解释某个候选、总结清单、改预算、改条件；改完真实重算 |
| 淘汰候选 | 默认折叠，可展开看违反了哪条硬性条件 |
| 阻塞项 | 直接显示阻塞原因，例如"没有召回候选""全部候选违反某条件" |

### 6.3 对话现在能做什么

当前对话是**本地确定性助手**，不接大模型，所有回答都从真实数据里取：

| 说法 | 行为 |
| --- | --- |
| `为什么推荐 TPS5450DDAR` | 逐条列出该候选的满足/不满足/未知与出处 |
| `查一下 LM358` | 走器件目录精确查询，返回类别、厂商、核心等级、C 编号 |
| `把 SEL-002 的输出电流改成 800mA` | 改偏好条件并重算清单 |
| `预算改成 100` | 改全局预算并重算 |
| `保留 TPS5450DDAR` / `排除 X` | 记录用户决定 |
| `总结一下当前清单` | 汇总各选型项的主推与阻塞 |

接大模型时保留这套工具边界即可：模型只负责把用户说法翻译成条件，
检索、判定、证据仍然由本阶段代码负责。这样不会出现"模型凭记忆报型号"。

## 8. 交付与交接

### 8.1 三份交付物

阶段产出刻意拆成三份，因为它们是三种不同性质的状态，混在一起会互相污染：

| 文件 | schema | 性质 |
| --- | --- | --- |
| 候选清单 | `pcbagent.candidate_set.v1` | 检索与判定的结果，**本阶段不改写** |
| 用户决定 | `pcbagent.device_decisions.v1` | 用户操作的结果，键为 `选型项::型号` |
| 下游交接 | `pcbagent.netlist_input.v1` | 由前两者合成，是流程之间的契约 |

用户决定单独落盘（`output/decisions.json`），服务重启不丢。这直接对应设计文档
「器件资料核验状态与用户选择状态分别记录」的要求：候选上的
`verification_status` 由证据决定，`user_decision` 由用户决定，两者各自独立。

### 8.2 交接规则

`src/handoff.py` 把候选清单与用户决定合成下游输入，规则如下：

1. **只有 `confirmed`（已确认）和 `keep`（保留）的候选会被导出**；待讨论和排除
   一律不导出。
2. 一个选型项如果没有任何选定器件，**不导出该模块**，并写进
   `diagnostics.skipped` 说明原因（是没做决定，还是决定都是排除/待讨论）。
3. 已经判定为 `excluded` 的候选即使被点了确认也会被拦下，不导出。
4. 器件既没有型号也没有料号时拒绝导出，不用占位件凑数。
5. 导出后立即调用下游官方校验器
   `netlist_end_to_end.generation_input.validate_generation_input`；校验不过就
   整个失败并保留诊断信息，不产出半成品。

下游契约的硬要求（来自 `generation_input.py`）：至少 1 个、最多 128 个 module，
每个 module 必须有非空且唯一的 `id` 和 `name`，`selected_devices` 非空，每个器件
必须有 `model` 或 `supplier_part`。实测导出结果可以带着 `supplier_part`
（立创 C 编号）通过校验。

### 8.3 界面上的入口

网页顶部「交付与交接」区提供两个按钮：查看最终候选清单、导出下游交接文件。
导出后直接显示校验结果与被跳过的项及原因。

## 9. 与现有代码的关系

现有器件选型代码在 `legacy/`（2026-10-14 退役归档）。复用与改动的分工：

| 现有代码 | 复用方式 |
| --- | --- |
| `device_selection/contracts.py` 的五个 schema | 保留结论语义（`fit` / `confidence` / `matched_requirements` / `risks` / `missing_evidence`） |
| `agents/device_evaluator.py` 的判定原则 | 完整继承：候选必须来自输入，证据缺失标未知，critical 失败不推荐 |
| `presets.py` + `assets/preset_components.json` | 直接复用，本阶段用于成本参考 |
| `stage.py` 的流程骨架 | 沿用「类别 → 参数 → 预算 → 评审」顺序 |

必须改的部分：

1. **输入契约**。现有代码吃的是 `requirement_intent` 的 `report` + `report_markdown`，
   新设计吃 `RequirementSpec`。这一层要新写适配，不能直接套。
2. **候选来源**。现有 `device_evaluator` 只核验输入里已有的型号，没有候选召回，
   实测 25 个模块里 11 个交不出结果。本阶段补上按 `leaf_code` 的类别召回。
3. **预算环节**。现有代码有 `budget_extractor` / `budget_allocator` 两个大模型步骤；
   本阶段先不做预算分配，只标注成本证据状态，等价格数据源确定后再补。

## 10. 风险与待办

| 风险 | 现状 | 处理 |
| --- | --- | --- |
| 单位归一化 | 98% 的数值没有单位列；已用文本优先策略兜住 | 把解析失败的字段定期导出复核 |
| 无价格数据 | 目录里根本没有价格 | 需要确定采购价格数据源；当前用预设库兜底并标待确认 |
| 远端共享账号 | TCP 可达，密码在 chenxin 的 0600 文件里，本账号读不到 | 找 chenxin 提供密码或导出只读账号 |
| 类别召回质量 | 依赖 `leaf_code` 是否齐全 | 暂无候选的类别列进阻塞清单，人工确认映射 |
| 需求侧尚未定稿 | `RequirementSpec` 目前是本阶段自拟 | 与需求分析侧对齐字段后更新，`schema` 版本号同步升 |
| 大模型尚未接入 | 对话是本地确定性实现 | 接入时保留工具边界，检索与判定不下放给模型 |

## 11. 测试案例库

### 11.1 为什么要有

会议要求「固定测试用例，观察优化前后 AI 回答是否符合预期」。器件选型需要一个
可重复的回归口径，否则每次改召回或判定逻辑都只能靠肉眼抽查。

### 11.2 素材与转换口径

素材是 34 份真实的历史选型产物
（`workspace/web/output/case*/console/stages/03_device_selection__*.json`），
每个模块带 `estimated_parameters`（含 `importance` / `value` / `unit` / `tolerance`）
和当时选中的器件。`tools/build_cases.py` 按下面的口径转换：

| 历史内容 | 转成什么 |
| --- | --- |
| `importance = critical` 的参数 | 硬性条件 |
| `importance = important` 的参数 | 偏好条件 |
| `importance = optional` 的参数 | 不进条件，记进 `meta.json` |
| `confirmed_device` | 选型项的指定器件，意图记为「仅作参考」 |
| 当时选中的器件 | `expected.json` 的对照基线 |
| 参数名对不上数据库字段 | 不硬塞，记进 `meta.json` 的 `unmapped_parameters` |

两个细节值得记下来：

- **单位以历史参数自带的 `unit` 字段为准**，再换算到基准单位。曾经漏用这个字段，
  把 `switching_frequency` 的 `300 kHz ~ 1 MHz` 当成 `300~1000 Hz`，差了三
  个数量级。
- **历史运行失败（agent 报错）的产物没有模块，必须跳过**，不能灌进案例库污染
  基线。当前有 3 份这样的产物，原因记录在 `cases/index.json` 的
  `skipped_sources`。

### 11.3 规模与基线

当前 **31 个案例、527 个模块、1347 条硬性条件、613 条偏好条件**，2368 条参数
尚未映射到数据库字段（保留在案例 meta 里，补一条映射就多一块覆盖）。

全量回归结果（`tools/run_cases.py`，2026-10-16）：

| 指标 | 数值 |
| --- | --- |
| 选型项 | 527 |
| 本次给出推荐 | 362（69%） |
| 阻塞 | 165 |
| 历史选出过器件的模块 | 220 |
| 首选与历史一致 | 66（30%） |

### 11.4 数字怎么读

- **覆盖率 69% 是进步**：历史实现只核验输入里已有的型号，没有候选召回，大量模块
  直接交白卷。补上按 `leaf_code` 的类别召回后，能给出推荐的比例明显提高。
- **首选一致率 30% 是问题**：当前排序只按「是否推荐 + 证据完整度 + `device_id`」，
